# Проверка личной записи через Checkfrod

LMS использует существующий HTTP-сервис Checkfrod, который подключён к боту
Советника. Точка совместимости: `105.sovetnik/app/src/checkfrod/client.ts`.
Сервис получает запись после отдельного действия владельца, обрабатывает её
асинхронно и предоставляет собственный подписанный отчёт. Исходники сервиса и
бота этой интеграцией не изменяются.

На стороне LMS нужны серверные `CHECKFROD_API_KEY`, `CHECKFROD_API_URL`
(по умолчанию `https://checkfrod.nadtocheev.ru`) и корректный публичный HTTPS
`NEXT_PUBLIC_SERVER_URL`. URL сервиса должен содержать только origin, без пути,
query, fragment и встроенных credentials. API-ключ используется в Bearer header,
не передаётся в браузер, отчёт или логи. HTTP redirects запрещены.

API определяет владельца через числовой `X-ICheck-User` и исторически хранит
его в пространстве `telegram:<id>`. Для LMS выделен диапазон
`9000000000000000 + LMS user ID`: положительный PostgreSQL int32 даёт уникальную
16-значную строку. Расчёт выполняется через BigInt. Этот диапазон выше максимума
52-битного Telegram ID, указанного в [официальном контракте User](https://core.telegram.org/bots/api#user),
поэтому задачи LMS не совпадают с задачами пользователей бота. В заголовок
не подставляется Telegram ID из профиля ученика. Менять этот способ вычисления
после появления задач нельзя без миграции удалённого ownership.

Клиент вызывается только после проверки сессии и владельца личной записи.
Библиотечные записи ментора и других людей на проверку не отправляются.
Изоляция API-ключом и namespace не заменяет эту проверку внутри LMS.

Перед отправкой workflow сохраняет момент начала отправки и уникальное имя
`lms-<recording-id>-<attempt>-<UUID>.mp4`. POST `/api/imports` получает
`{ url, consent: true, roi_spec }`. URL — подписанный callback самого LMS:
`/api/internal/interviews/<id>/<unique-name>?expires=<Unix seconds>&token=<HMAC>`.
Callback ограничен одной записью, владельцем и попыткой; подпись и срок проверяет
серверный route. Клиент проверяет origin, форму пути, совпадение ID, попытку 1–3,
UUID, формат подписи и два допустимых параметра. HTTP localhost разрешён только
в тестовом окружении. Срок доступа к исходнику — до 24 часов.

Клиент принимает только подготовленный workflow callback. Оригинальные временные
ссылки Яндекс Диска и произвольные ссылки от ученика для import не используются.
Это позволяет сервису начать скачивание после ожидания очереди, когда адрес CDN
Яндекса уже мог измениться. Callback выдаёт защищённый видеопоток без OAuth.

На текущем сервисе POST import не имеет идемпотентности. Клиент никогда
автоматически его не повторяет. Потерянный ответ или успешный ответ без корректного
ID помечается `submissionUncertain`; workflow должен искать уже созданную задачу
через owner-scoped GET `/api/jobs` по точному уникальному имени файла. Временные
ошибки GET можно повторять, продолжая ту же задачу. Не подтверждённая отправка
не должна запускать второе импортирование автоматически.

Опрос GET `/api/jobs/<id>` принимает состояния uploading, queued, running, done,
failed. Progress — доля 0–1. Клиент сохраняет только безопасные поля состояния;
произвольные диагностические тексты сервиса пользователю не передаются. Ответы
API ограничены четырьмя МиБ фактически прочитанных байтов. Таймаут 20 секунд
действует на запрос и получение тела ответа, включая JSON отчёта.

Готовый `/reports/<id>/report.json` остаётся серверными данными. Сводка повторяет
семантику бота: эпизоды `confidence: info` исключены из сигналов; отдельно
считаются моменты для просмотра, минуты по радужке/голове, только по голове,
без лица и с застывшим видео. Отсутствующие старые поля дают ноль; отрицательные
и нечисловые значения не становятся результатами анализа. Количество сигналов
показывает моменты, которые нужно просмотреть в записи, и не устанавливает
факт посторонней помощи.

POST `/api/jobs/<id>/link` выпускает ссылку на собственный отчёт Checkfrod.
Принимается только HTTPS URL на том же origin с путём `/r/<token>`, без query,
fragment и credentials, со сроком доступа от 1 секунды до 7 суток. Workflow
проверяет владельца перед выдачей свежей ссылки; подписанная ссылка требует
такого же обращения с приватностью, как и сама запись.

DELETE `/api/jobs/<id>` применяется к разрешённой удалённой задаче перед удалением
локального документа. Ответ 404 идемпотентен; 409 сохраняется как отказ, чтобы
работающая задача не выглядела удалённой. Не завершённые внешние операции должны
сохранить локальный документ и информацию для последующей очистки.

Unit-тесты используют только подменённый fetch. Они проверяют namespace,
ownership headers, callback и report URL guards, отсутствие POST retry,
uncertain submission, ограничения JSON, отмену и таймаут тела ответа, совместимость
сводки и owner-scoped восстановление. Создание реальной задачи Checkfrod этими
тестами не выполняется.
