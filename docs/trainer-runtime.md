# Go, Python и frontend в тренажёре

Новые языки работают через отдельный доверенный gateway `trainer-runtime/`.
JavaScript и TypeScript сохраняют существующий серверный V8-изолят.
Контейнеры решений не имеют сети, переменных окружения LMS, Docker socket
или доступа к данным платформы. Прогресс по всем языкам пишет только
`/api/trainer/submit` по результату серверной проверки.

## Запуск и проверка локально

Нужен Docker. Команда собирает образы Go, Python, браузера и Next.js, открывает
одноразовый gateway только на loopback, проверяет изоляцию и весь новый каталог:

```sh
pnpm test:trainer-runtime --build
```

Токен генерируется в памяти, после проверки gateway и Next-сессии закрываются.
Повторный прогон использует собранные образы: `pnpm test:trainer-runtime`.
Ошибки Docker, отсутствие образов или недоступный компилятор завершают
проверку ошибкой. Эталон каждой задачи обязан пройти все проверки, стартовый
шаблон обязан получить `failed`.

Полный интеграционный прогон дополнительно проверяет настоящие маршруты LMS,
HTTP gateway и запись прогресса в отдельную одноразовую PostgreSQL:

```sh
pnpm test:integration:runtime --build
```

После сборки образов достаточно `pnpm test:integration:runtime`. Команда
включает проверки изоляции и всего каталога, затем проверяет публичные и
собственные кейсы Go/Python, скрытые DOM/CSS-проверки и обработчики React. Публичный
запуск не записывает прогресс; клиентский `passed` не обходит скрытые кейсы;
настоящий серверный успех начисляет XP однократно. Проверяются также запрет
доступа и отказ gateway без записи прогресса. Компилятор, браузер, HTTP и
Payload не подменяются. Этот полный набор запускается в отдельной задаче CI.

Для работающего приложения нужны `TRAINER_RUNTIME_URL` и
`TRAINER_RUNTIME_TOKEN` (случайный токен минимум 32 символа). Gateway
слушает порт 3100, принимает этот токен и ограничивает одновременные запуски.
`TRAINER_MAX_CONCURRENT` принимает 1 или 2 и ограничивает также число активных
сессий Next.js. Compose по умолчанию использует 1 для экономии памяти;
увеличивайте лимит только после проверки ресурсов Docker-хоста.
Для локальной разработки gateway можно запустить `node trainer-runtime/server.mjs`
с тем же токеном, а URL приложения направить на `http://127.0.0.1:3100`.
Не публикуйте gateway в интернете.

## Подключение в Dokploy

Runtime входит в основной `docker-compose.yml` и выкатывается штатно из Git.
Приложение ждёт healthy gateway; gateway ждёт успешного создания ключа и
старта четырёх контейнеров, удерживающих job images. Они остаются запущены с
пустым таймером Node, без сети и с корнем только для чтения; решения в них
не выполняются. Лимит каждого — 64 МБ. Завершённые держатели могут быть удалены
очисткой вместе с неиспользуемыми образами, после чего gateway отвечает 503.
Постоянная ссылка работающего контейнера сохраняет образ для новых задач.
Семантика зависимостей описана в [документации Compose](https://docs.docker.com/compose/how-tos/startup-order/).

При первом запуске init создаёт отдельный случайный ключ (32 байта) в закрытом
томе `lms-trainer-auth`: `/trainer-auth/token`, владелец `1001:1001`, права `0440`.
Публикация файла атомарная; повторный выкат сохраняет прежний ключ.
Приложение и gateway монтируют том только для чтения. Приложение загружает ключ
в `TRAINER_RUNTIME_TOKEN` до запуска Next; gateway читает тот же файл.
Gateway работает как `0:1001` без capabilities: группа позволяет читать ключ,
UID 0 нужен для доступа к Docker socket. Init имеет только CHOWN/FOWNER.
Ключ, том и socket не передаются контейнерам решений.
Порт gateway не опубликован; связь с приложением идёт через отдельную
[внутреннюю сеть](https://docs.docker.com/reference/compose-file/networks/#internal).

Для этого подключения API-ключ панели Dokploy не требуется. Environment
может переопределить URL и общий токен при использовании своего gateway;
непустой `TRAINER_RUNTIME_TOKEN` имеет приоритет над файлом у обеих сторон.
Старый дополнительный `docker-compose.trainer-runtime.yml` совместим с основным
файлом, но отдельное включение runtime больше не нужно.
После миграции и проверки работающего приложения новые задачи нужно загрузить
из кодового каталога через авторизованный Payload API либо `pnpm seed:trainer`
на явно выбранной БД. Последний выполняет upsert всего каталога и перезаписывает
CMS-правки каталожных задач; перед запуском учитывайте это.

При самостоятельном запуске gateway вне Compose соберите четыре job image
на Docker-хосте, на котором он работает:

```sh
docker build --target go-job -t lms-trainer-go:local trainer-runtime
docker build --target python-job -t lms-trainer-python:local trainer-runtime
docker build --target frontend-job -t lms-trainer-frontend:local trainer-runtime
docker build -f trainer-runtime/Dockerfile.next -t lms-trainer-next:local trainer-runtime
```

Имена можно переопределить через `TRAINER_GO_JOB_IMAGE`,
`TRAINER_FRONTEND_JOB_IMAGE`, `TRAINER_NEXT_JOB_IMAGE`. Gateway запускает
только эти заранее установленные образы, без скачивания зависимостей на запрос.
Временные контейнеры имеют лимиты CPU, памяти, процессов, диска, времени и вывода.
Проверьте свободную память хоста: одновременно могут работать контейнеры
компилятора/серверного проекта и браузера, каждому нужен отдельный лимит памяти.

Docker socket доступен только доверенному gateway и даёт ему административные
права Docker. Для отдельной инфраструктуры выполнения предпочтителен выделенный
Docker-хост; приложение LMS обращается к нему по закрытому HTTP-адресу с токеном.
Сокет и токен никогда не передаются контейнерам решений. Изменения Kubernetes
для этой среды не требуются и запрещены пользовательским правилом проекта.

## Формат задач

Go использует `checkMode: program`, `starterCodeGo`, `solutionCodeGo` и
`runtimeCases`: `{name, hidden, input, expected}`. Решение — полная программа
`package main`. Она читает текст из stdin и пишет результат в stdout.
Ожидаемый вывод сравнивается доверенным gateway, вне программы пользователя.
Доступна стандартная библиотека; внешние модули и сетевые запросы отключены.

Python 3.13 использует тот же `checkMode: program`, но поля
`starterCodePython` / `solutionCodePython` и образ `TRAINER_PYTHON_JOB_IMAGE`
(по умолчанию `lms-trainer-python:local`). Полный `main.py` читает stdin и пишет
stdout; доступны только стандартные модули. Синтаксис проверяется без исполнения
кода, каждый пример запускается в новом контейнере и новом процессе CPython
с `-I -S -X utf8 -u`, пустым окружением. Сеть, установки pip, секреты LMS,
Docker socket и запись в корень образа недоступны. Превышение времени, памяти
или вывода не даёт зачёт; скрытый ввод/вывод и исключения скрытого кейса не
попадают ученику. В комнатах Python также поддерживает console-only запуск.

Frontend использует `checkMode: dom`, `starterFiles` и `solutionFiles`:
объекты «относительный путь → код». До 32 файлов, общий JSON решения до
20 000 символов. HTML/CSS начинается с `index.html`, React — с `App.tsx`
(default export компонента), Next.js — с `app/page.tsx` и `app/layout.tsx`.
Решение хранится как JSON файлов, черновики и история прогресса сохраняются.
Поддерживаются CSS Modules (`Button.module.css`) и catch-all страницы Next.js
(`app/[...slug]/page.tsx`). Для совместимости также заполните резервное
`starterCode` кодом Go/Python либо JSON файлов; кодовый сидер делает это автоматически.

Проверки `runtimeCases[].checks` — последовательность декларативных шагов:

```json
[
  { "selector": "button", "action": "click" },
  { "selector": "button", "action": "press", "value": "Enter" },
  { "selector": "output", "text": "1" },
  { "selector": ".card", "css": { "display": "flex" } }
]
```

Также доступны `fill` с `value`, `count`, `visible`, `attribute: {name,value}`.
`viewport: {width,height}` задаёт окно для адаптивной вёрстки,
`path` задаёт страницу/параметры Next.js (например `/?q=react`).
Каждый серверный кейс запускается в новом браузерном контексте;
ожидаемые свойства и итоговый вердикт находятся вне iframe пользователя.
Скрытые строки закрыты field access, исключены из публичного запуска и
не раскрывают входные данные/ожидаемые значения в сообщениях результата.

## Next.js

Запускается настоящий App Router: серверные и клиентские компоненты,
локальные route handlers, файлы в `app/`, `components/`, `lib/` и `src/app/`.
Next.js/React/TypeScript установлены заранее. Произвольный package.json,
скрипты установки, конфиг Next.js и внешние пакеты не исполняются.
Код сервера работает в отдельном контейнере; браузер проверки — в другом.
HTTP между ними передаётся доверенным RPC без открытия сетевого доступа.

При повторном запуске, смене языка и выходе предыдущий контейнер предпросмотра
освобождается; оставшиеся сессии автоматически истекают. Предпросмотр выдаётся
после авторизованного запуска как короткоживущий
непредсказуемый токен. `/api/trainer/preview/<token>/` передаёт только запросы
к соответствующему контейнеру, не пересылает cookies/авторизацию LMS и
не принимает внешний URL. Ответы имеют CSP `sandbox allow-scripts allow-forms` и `form-action 'none'`,
iframe также не получает `allow-same-origin`. После истечения ссылки
нажмите «Запустить» повторно. Прокси не сохраняет прогресс.

Первый запуск Go/Next.js включает компиляцию, поэтому дольше обычного JS.
HTML/React собираются один раз на публичный запуск вместе с предпросмотром.
Внешняя сеть, серверные интеграции и установка npm/Go/Python-зависимостей не доступны.

Для `press` разрешены только Enter, Escape, Space, ArrowLeft, ArrowRight,
ArrowUp, ArrowDown, Home, End, Tab. Проверка исполняется на указанном элементе.
Произвольные сочетания клавиш не принимаются. Фильтры формата и источники
компаний описаны в [каталоге собеседований](trainer-interview-sources.md).

События submit формы поддерживаются в opaque iframe через allow-forms.
Фактическую отправку формы блокирует доверенная CSP form-action none;
allow-same-origin, навигация родителя и доступ к DOM платформы не разрешены.
Это нужно, чтобы стандартный React onSubmit/preventDefault работал так же,
как в обычном приложении, без сетевой отправки данных учеников.
