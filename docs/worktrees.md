# Параллельная работа в worktree

Каждая задача ведётся в своём git worktree рядом с `app/`: `107.lms/wt-<имя>`. Ветки в
`app/` и в чужих деревьях не переключаются: в этот момент с теми же файлами может работать
соседняя сессия агента, и переключение подменит ей код посреди работы.

```sh
pnpm wt:new feat/<задача>    # ../wt-<задача> от свежего origin/main, зависимости, база и порты
pnpm wt:setup                # подготовить уже созданное дерево; повторный запуск безопасен
pnpm wt:list                 # все деревья: ветка, дата, порты, влита ли ветка, есть ли правки
pnpm wt:remove wt-<задача>   # удалить дерево, его тестовые базы и ветку, если она в origin/main
```

`wt:new` и `wt:remove` работают из любого checkout. Если ветка уже есть, `wt:new` открывает
дерево на ней, а не создаёт новую.

## Что делает wt:setup

Выбирает свободный слот от 1 до 99 и записывает его настройки в `.worktree.env` (в git не
попадает). Тесты читают этот файл сами, явно заданная переменная окружения главнее файла.

| | Основной checkout | Дерево в слоте N |
|---|---|---|
| База интеграции | `lms_integration` | `lms_wtN_<имя>`, плюс `_seed` и `_migrations` |
| e2e: приложение и лендинг | 3100, 3101 | 4000 + 10·N и следующий |
| Скриншоты: приложение и лендинг | 3102, 3103 | 4000 + 10·N + 2 и + 3 |
| База e2e и скриншотов | `lms_e2e_3100`, `lms_e2e_3102` | `lms_e2e_<порт приложения>` |

Все базы живут в одном контейнере `lms-test-pg` (порт 55433): у деревьев отдельные базы, а
не отдельные серверы PostgreSQL. Слот выбирается так, чтобы его порты были свободны в момент
настройки.

Дальше `wt:setup` ставит зависимости (`pnpm install --frozen-lockfile --prefer-offline`)
и создаёт `.env`, если его нет: `DATABASE_URL` на базу дерева и случайный `PAYLOAD_SECRET`.
Этого хватает для `pnpm build` и `pnpm smoke`. Существующий `.env` не меняется.

Без своего порта и базы пока остаются:
- `pnpm test:integration:runtime`: база `lms_runtime_integration` и Docker-задачи общие,
  два прогона одновременно не запускать;
- `pnpm dev`: порт 3000 и база из `.env`.

## Очередь тяжёлых проверок

`lint`, `typecheck`, `test`, `test:*` (кроме `test:watch` и `test:prod`) и `build` запускаются
через `scripts/heavy.sh`, который передаёт команду утилите
[heavy](https://github.com/mokevnin/heavy). Это общий на всю машину счётчик мест. Когда все
места заняты, команда ждёт и пишет, кого ждёт:

```
heavy: all 3 slots of pool 'default' are busy, waiting for one
heavy:   slot 0: held by pid 40643 for 12s: tsc --noEmit
```

Это штатная очередь, а не зависание. По умолчанию мест четверть от числа ядер, на 14 ядрах
это 3. Число мест меняет `HEAVY_SLOTS`, кто их держит, показывает `heavy --status`. Дольше
15 минут команда не ждёт и запускается без места (`HEAVY_TIMEOUT`, `HEAVY_ON_TIMEOUT`):
агент, который ждёт за чужим e2e, иначе упёрся бы в таймаут своей команды.
Вложенные вызовы второй раз не ждут: e2e уже держит место, когда внутри собирает приложение.
В CI и на машине без heavy команда запускается сразу. Установка: `brew install mokevnin/tap/heavy`.

Сборка образа в Dockerfile вызывает `npx next build` напрямую и от heavy не зависит. Проверка
мимо pnpm-скриптов (`pnpm exec vitest run …`) идёт без очереди; для неё есть `heavy -- <команда>`.

## Место на диске

Пакеты лежат в общем сторе pnpm и в деревья только подключаются. Больше всего места в дереве
занимают `.next` (1-2 ГБ после сборки) и `landing/node_modules` (около 170 МБ, npm). Их
ставит `scripts/landing-server.mjs` при первом e2e. `wt:remove` удаляет их вместе с деревом.

## Завершение задачи

Когда ветка выкачена в `main`, удалите дерево: `pnpm wt:remove wt-<задача>`. Команда
откажется, если в дереве есть незакоммиченные или неотслеживаемые файлы. Ветку она удаляет,
только если та уже в `origin/main`. Чужие деревья не удаляйте; `pnpm wt:list` показывает,
какие ветки влиты и где остались правки.
