# Тренажёр задач

Мини-версия LeetCode внутри платформы: пользователь решает задачу на JavaScript
или TypeScript в редакторе Monaco, прогоняет тесты и получает разбор, какой
именно тест упал, с какими данными и на какой строке.

## Как устроена проверка

Проверка выполняется дважды и намеренно по-разному.

| | «Запустить» | «Отправить» |
|---|---|---|
| Где | Браузер, sandboxed-iframe | Сервер, V8-изолят |
| Что прогоняется | Только публичные тесты | Полный набор, включая скрытые |
| Скорость | Мгновенно | 50–150 мс |
| Влияет на прогресс | Нет | Да — это единственный источник истины |

Клиентский результат на сервер не отправляется вообще. `POST /api/trainer/submit`
получает только код, пересобирает скрипт из своей копии тестов и запускает его
сам. Накрутить баллы прямым запросом невозможно.

## Песочницы

Один и тот же харнесс (`src/lib/trainer/harness.js`) исполняется в трёх местах:

- **iframe** в браузере — `sandbox="allow-scripts"` без `allow-same-origin`,
  то есть уникальный непрозрачный origin без доступа к cookies и API платформы;
- **isolated-vm** на сервере — свежий V8-изолят без `require`, `process` и `fs`,
  с лимитами памяти (32 МБ) и времени;
- **node:vm** в тестах — там же прогоняется весь каталог задач.

Таймеры во всех трёх хостах виртуальные: `setTimeout`, `setInterval` и
`Date.now` подменены управляемыми часами. Без этого в изоляте асинхронный код
не работал бы вовсе (там нет event loop), а тесты на `debounce`, `throttle` и
`retry` зависели бы от реального времени. Тесты двигают время через
`await __clock.tick(ms)` и `await __clock.runAll()`.

### Дочерний процесс

Изолят живёт не в процессе Next, а в отдельном процессе
(`src/server/trainer/runner-child.mjs`), который запускается с флагом
`--no-node-snapshot` и **пустым окружением**. Даже при гипотетическом побеге из
изолята рядом нет ни `DATABASE_URL`, ни `PAYLOAD_SECRET`. Зависший процесс
убивается и поднимается заново, веб-сервер этого не замечает.

Пулом управляет `src/server/trainer/pool.ts`: два процесса, очередь заданий,
жёсткий таймаут, перезапуск по таймауту.

## Режимы проверки задачи

| `checkMode` | Как проверяется |
|---|---|
| `unit` | Прогон тестов: табличные кейсы и/или код на API харнесса |
| `types` | Только компилятор TypeScript: решение верно, когда tsc не выдал ни одной диагностики |
| `stdout` | Легаси: сравнение вывода `console.log` с эталоном |

## Каталог задач

Каталог лежит **кодом** в `src/data/trainer/` — по файлу на тему. Рядом с
каждой задачей лежат её тесты и эталонное решение, поэтому
`tests/unit/trainer/catalog.test.ts` на каждом `pnpm test` проверяет:

1. эталонное решение проходит все свои тесты;
2. стартовый шаблон их **не** проходит;
3. эталон на TypeScript компилируется без диагностик в strict-режиме.

Сломанную или тривиальную задачу закоммитить не получится.

Заливка в БД: `pnpm seed:trainer`. Сидер идемпотентен, ищет по slug и
обновляет. Задачи, которых больше нет в каталоге, он не удаляет — на них может
висеть прогресс пользователей, — а только сообщает о них.

**Важно:** запускать сид на боевой БД нужно отдельно от работающего приложения.
`payload run` в dev-режиме добавляет в `payload_migrations` строку `dev` с
`batch = -1`, и следующий запуск приложения в production остановится на
интерактивном вопросе. Если это случилось — удалите эту строку.

## Добавление задачи

1. Открыть нужный файл темы в `src/data/trainer/`.
2. Добавить объект задачи: `slug`, `title`, `difficulty`, `descriptionMd`,
   `starterCode`, `solutionCode`, тесты, `solutionNotes`.
3. Для TypeScript добавить `languages: ['js', 'ts']`, `starterCodeTs`,
   `solutionCodeTs`. Если у задачи есть преамбула на JavaScript, добавить
   `setupTypes` с `declare`-объявлениями — иначе strict-режим tsc будет ругаться
   на неявный `any` в фикстурах.
4. `pnpm test` — каталог-тест проверит задачу.
5. `pnpm seed:trainer` — залить.

Табличные кейсы пишутся обычными JS-значениями; в код литералов их переводит
`toLiteral` (`src/lib/trainer/literal.ts`). Функции и конструкторы литералом не
выражаются — для них есть `raw('...')`.

## Что требуется от окружения

- **Node 22.** `isolated-vm` не собирается под Node 20: там нет
  `v8::SourceLocation`. Базовый образ — `node:22-alpine`, в стадии `deps`
  доставляются `python3 make g++ linux-headers` для сборки нативного модуля.
- **Ассеты Monaco** копируются в `public/monaco/vs` скриптом
  `scripts/copy-monaco.mjs` (хуки `predev` и `prebuild`). CDN не подходит:
  CSP сайта разрешает только `connect-src 'self'`.
- **Харнесс** вшивается строкой в `harness-source.generated.ts` скриптом
  `scripts/build-harness.mjs`. Файл закоммичен; тест
  `tests/unit/trainer/harnessSource.test.ts` падает, если он разошёлся с
  исходником.
- `isolated-vm` и `typescript` помечены в `next.config.mjs` как
  `serverExternalPackages` и копируются в образ отдельным шагом: в
  standalone-вывод Next они не попадают.

Сборка образа проверяет песочницу на месте: если нативный модуль не собрался
или ассеты не доехали, `docker build` падает, а не отдаёт сломанный образ.
