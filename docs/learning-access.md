# Назначения учебного доступа

## Модель и совместимый выкат

В отдельной политике пользователя `learning-access-policies` хранится режим обучения; `Users.learningAccessMode` служит его отображением в форме:

- `all` — все опубликованные материалы; существующие пользователи сохраняют этот режим при миграции.
- `assigned` — режим по умолчанию для новых аккаунтов. Содержимое закрыто, пока нет активного разрешающего назначения. Отдельная настройка видимости определяет, видны ли закрытые программы; содержимое закрытого материала не передаётся браузеру.

Совместимость обеспечивают две официально сгенерированные миграции: первая добавляет колонку с default `all`, сохраняя существующие записи; вторая меняет только default на `assigned`, не меняя старых пользователей. Seed/E2E legacy-фикстуры явно указывают `all`; проверка реального создания нового аккаунта без поля требует `assigned`.

Отсутствующий, пустой или неизвестный режим никогда не означает `all`. Чистая политика выбирает `assigned`; серверный resolver для частичного User DTO получает действительный режим и роль из БД. Совместимость прежних пользователей обеспечивается явным `all` в миграции, а не небезопасным fallback при отсутствии поля.

Политика имеет уникальную связь `user`, режим `mode` и роль `role` (`admin`/`student`). Она создаётся при создании аккаунта, даже с `skipHooks`, и меняется только внутренними защищёнными хуками в транзакции пользователя. Прямые REST create/update/delete запрещены. Для прежнего пользователя без этой строки единственный совместимый fallback — текущая запись БД Users; первое административное изменение режима или роли создаёт независимую политику. Неизвестная роль означает `student`.

Разделение учитывает особенность Payload 3.89: штатные login/logout/refresh/reset используют `db.updateOne` со старой полной копией пользователя и обходят `Users.beforeChange`. Независимую политику они изменить не могут. Дополнительно собственный декоратор PostgreSQL-адаптера ограничивает SDK записи сессий полями `sessions` и `updatedAt`, сохраняя текущие пароль, роль, режим, email и баллы. Каждая проверка допуска и роли администратора обращается к политике, даже если переданный DTO содержит `all`/`admin`. `Users.afterRead` отражает актуальные режим/роль, а JWT Authentication загружает именно этот нормализованный документ; неподтверждённые JWT claims не дают административных прав.

Поле создаёт/меняет только администратор. Права берутся из действительной независимой политики, а не из присланного `userId`, зеркальных полей формы, старой копии User или localStorage. `Users.read` разрешает ученику только собственную запись; лидерборд использует отдельную минимальную серверную проекцию без email.

`learning-access-grants` хранит ученика, полиморфную цель (`roadmaps`, `roadmap-nodes`, `courses`, `sections`, `lessons`, `trainer-topics`, `trainer-tasks`), действие `allow`/`deny`, необязательные `startsAt`/`expiresAt` и комментарий. Сервер вычисляет уникальный `ruleKey = user:targetCollection:targetId`: у ученика одно редактируемое правило на конкретную цель, а не накапливающиеся дубли.

## Настройка в админке

Откройте **Назначения обучения**, выберите ученика и настройте три независимых параметра:

1. **Доступ к курсам и урокам** — только назначенное или все опубликованные материалы с исключениями.
2. **Что ученик видит в каталоге** — все программы или только назначенное. При «Показывать только назначенное» неназначенные курсы, разделы, уроки и задачи не появляются в каталогах, поиске, родительских программах и по прямой ссылке. Роадмап с доступным фрагментом показывает только соответствующую часть; пустые программы скрыты.
3. **Доступ к тренажёру** — только назначенные задачи, весь опубликованный тренажёр с исключениями или полное выключение. Назначение темы открывает её опубликованные задачи, включая новые. Отдельное назначение задачи имеет приоритет над темой. Выключенный тренажёр закрывает все задачи даже при сохранённых разрешениях; сами разрешения сохраняются для последующего включения.

Для примера: назначьте Backend целиком, откройте только тему тренажёра «Асинхронность», закройте одну задачу внутри неё и включите показ только назначенного. Ученику будут видны Backend и оставшиеся разрешённые задачи; остальные программы скрыты. Назначение отдельного урока открывает его необходимый путь через курс и роадмап, не раскрывая соседние уроки.

Если историческое назначение осталось без цели после удаления материала, manager отвечает 409 и предлагает открыть стандартный список назначений. Удалите правило с пустой целью и обновите ученика; manager не пропускает такое правило молча и не применяет неполный набор назначений.

Для тем и задач тренажёра действуют те же дата начала, дата окончания и комментарий. При выборе задачи список можно ограничить её темой. Административный поиск возвращает только ID, название и признак публикации, без стартового кода, тестов и решений.

**Посмотреть доступ по курсам** показывает результат текущих несохранённых правок: открытые, частичные, закрытые и скрытые курсы, а также число доступных задач тренажёра. Курсы и задачи имеют независимую пагинацию. Только **Сохранить назначения** применяет настройки и правила одной транзакцией; ошибка откатывает всё. При конфликте с другим администратором правки сохраняются в форме, но требуется загрузить актуальные назначения. **Отменить изменения** восстанавливает все три настройки и правила.

Новые аккаунты по умолчанию получают `learningCatalogVisibility: assigned` и `trainerAccessMode: assigned`: без назначения нет доступных программ или задач. Прежние аккаунты с отсутствующими новыми полями сохраняют `catalog` / `all`; миграция не отзывает их права автоматически. Настройки хранятся в независимой политике (`catalogVisibility`, `trainerMode`), поля Users являются зеркалом. Опущенные в старом клиенте PUT параметры сохраняют текущие значения. Новые параметры участвуют в revision и аудите; ученик, старый JWT пониженного администратора и запоздавший SDK login/refresh не могут расширить ими доступ.

## Решение допуска

Приоритет: урок > раздел > курс > тема > роадмап > режим пользователя. Более узкое разрешение может открыть исключение внутри широкого запрета; узкий запрет закрывает материал внутри назначенного курса. При нескольких правилах одинаковой специфичности `deny` побеждает. Например, курс может принадлежать теме через `Courses.roadmapNode` и через `RoadmapNodes.course`; обе связи учитываются только при совпадении родительского роадмапа.

Время начала включительно, время окончания исключительно. Истёкшее или ещё не начавшееся правило не участвует. Неверная дата не даёт разрешения; сохранение неверного интервала отклоняется.

Для ученика всегда обязательны опубликованные урок, курс, роадмап и раздел, если он задан. Отсутствующий родитель, чужой раздел или тема курса из другого роадмапа закрывают доступ независимо от `allow`. У администратора явный обход для редактирования черновиков.

Назначение одного раздела/урока позволяет открыть страницу программы его курса, но не соседние материалы. Пререквизиты остаются рекомендацией порядка обучения: назначение доступа и требование предварительного прохождения — разные правила. Сертификат полного курса не должен выдаваться за назначенный фрагмент; знаменатель полного курса остаётся всеми его опубликованными уроками.

## Одна политика для REST и страниц

`src/lib/learning-access.ts` — чистая функция `buildLearningAccess`. `src/server/learning-access.ts` — загрузка минимальных метаданных и контракт:

- `getLearningAccess(payload, user, req?)` возвращает `lessonWhere`, `accessibleCourseIds`, синхронные `canAccessCourse(id)`, `canAccessLessonMetadata(lesson)`, `canBrowseCourse(id)`, `canBrowseLessonMetadata(lesson)`.
- `canAccessLesson`, `requireLessonAccess` принимают числовой ID либо **уже проверенную серверную проекцию**, никогда объект из тела HTTP-запроса. Числовой путь читает только ID/курс/раздел/публикацию, без `content`.
- `Lessons.access.read = lessonReadAccess` применяет тот же `Where` к Payload REST и Local API с `overrideAccess:false`. Привилегированный Local API по умолчанию обходит access: страницы и собственные route handlers обязаны явно использовать контракт перед чтением материала.

Снимок и нормализованная политика кешируются исключительно в `WeakMap` конкретного `PayloadRequest`, отдельно по ID пользователя. Межзапросного кеша допусков нет: следующий запрос увидит отзыв назначения без ожидания TTL. Изменение правил/режима/роли инвалидирует снимок текущего запроса. Не переиспользовать один `PayloadRequest` для долгоживущих фоновых задач.

Политика получает опубликованность и связи роадмапов/тем/курсов/разделов; из уроков читает **только цели явных исключений**. `lessonWhere` содержит не более трёх групп: разрешённые курсы без раздела, разрешённые разделы с опубликованным курсом, явные разрешения уроков. Число реляционных JOIN не растёт с количеством назначенных курсов. Один запрос метаданных отдельно возвращает только ID опубликованных уроков с отсутствующим разделом или несовпадающим курсом раздела; эти ID исключаются из общего фильтра. Он использует транзакцию `req`, не читает контент, а при более 10 000 испорченных связей закрывает доступ с 503. Все 5550+ уроков не загружаются для каждого запроса. Пагинация полная, с детерминированной сортировкой; защитный предел не возвращает частичный список при переполнении. Реальный REST-тест `learningAccessScale.test.ts` проверяет прогресс и заметки на 75 курсах, правила-исключения и чужой раздел, а также не более 12 JOIN в запросе прогресса.

Точечный `canAccessLesson`/`requireLessonAccess` для видео и Range не сканирует даже метаданные каталога: загружает независимую политику по уникальному индексу `user`, конкретные курс/роадмап/раздел, связанные с этим курсом темы через индекс `RoadmapNodes.course` и назначения одного ученика через индекс `user`. Он передаёт эти ограниченные данные в ту же чистую функцию политики. Если полный снимок уже построен в данном запросе, повторно используется он. `learningAccessServer.test.ts` проверяет эквивалентность каталожной и точечной политики, а также отсутствие полного сканирования и запроса `lesson.content`.

## Запись и отзыв

`guardLearningLessonWrite` стоит после `assignOwner`, до блокировки прогресса и начисления XP. Он проверяет исходный урок при PATCH даже без `lesson`, затем новый фактический урок. Ученик не может перемещать существующую запись на другой урок. Для ответа комментария урок сначала определяется корневой веткой; `restrictCommentThread` сохраняет принадлежность ученика своей ветке.

Чтение заметок, комментариев, прогресса, мест остановки и закладок сочетает ownership с тем же доступом к уроку. После отзыва их содержимое не раскрывается через REST/depth/populate. Закладки задач тренажёра проверяют собственное персональное назначение тренажёра, независимо от режима курсов.

Trusted maintenance Local API без пользователя сохраняет возможность seed/import: внешний REST всё равно требует authenticated actor. `skipHooks` не отключает проверку доступа у вошедшего ученика. Любые операции над назначениями требуют администратора даже через Local API.

## Аудит и конкурентность

Каждое create/update/delete назначения пишет снимок в `learning-access-audit` с тем же `req` и транзакцией. Изменение режима также сохраняет старое/новое значение. Ошибка записи аудита откатывает изменение; у внешнего API нет create/update/delete аудита. Hooks запрещают изменение/удаление аудита даже привилегированным Local API. Числовые снимки actor/user/target сохраняются после удаления исходных объектов; пароли, email, cookie, URL видео и комментарий администратора не попадают в аудит.

Изменение назначений сериализуется `pg_advisory_xact_lock(7204, userId)`; перенос правила между учениками блокирует IDs в возрастающем порядке. API массового назначения берёт эту блокировку, затем `users FOR UPDATE`. Обычные изменения пользователя берут только блокировку строки: это сохраняет порядок у тренажёра, уже удерживающего пользовательскую строку, и предотвращает цикл `users row → 7204 → users row`.

Payload заполняет отсутствующие поля PATCH значениями исходного документа **до** `beforeChange`; одно позднее сравнение режима с `originalDoc` поэтому не защищает от конкурентного отзыва. `beforeOperation` запоминает только имена фактически переданных полей без их значений, паролей и создания транзакции. После блокировки `beforeChange` заново читает текущую запись, применяет только явно переданные разрешённые поля и обновляет `originalDoc` для правдивого аудита. Профильный PATCH не восстанавливает старый `all`, а изменение комментария назначения не возвращает старый `allow`. Для изменения владельца назначения проверяется актуальный владелец; при его конкурентной смене операция получает 409 вместо захвата блокировок в обратном порядке.

Очистка связей удаляет назначения до удаления ученика/урока/раздела/курса/роадмапа/темы в той же транзакции. События удаления остаются в аудите.

OTel `recordLearningAssignment` описывает валидированную попытку до commit, а не подтверждённое изменение: Payload `afterChange` вызывается до завершения транзакции. Источник успешно зафиксированных назначений — таблица аудита. `recordLearningAccess` выдаёт решения допуска и задержки, используя только непрозрачные числовые IDs; метрики не содержат ID и других меток высокой кардинальности. Подробности — [learning-observability.md](./learning-observability.md).

## Защита видео и её предел

Каждый запрос видео/файла должен заново проверить этот же допуск, а не только факт входа или публикацию. Нельзя отдавать браузеру исходный Yandex URL либо переносимый CDN redirect. Медиа, связанное с закрытым уроком, не становится публичным из-за того, что оно обложка в другом месте. Самостоятельное угадывание lesson/block/media ID не предоставляет допуск.

Разрешённый зритель всё равно получает байты для воспроизведения и может записать экран/сохранить поток. Публичный источник на Яндекс.Диске остаётся доступен вне LMS людям, знающим прежнюю ссылку: полное закрытие источника требует отдельной проверенной миграции на приватное хранилище и отключения старых публичных публикаций. Ранее полученные файлы/байты отозвать невозможно.

## Проверки

`tests/unit/learningAccess.test.ts` проверяет иерархию, deny tie-break, обе связи темы, неконсистентные родители, публикацию, срок, admin bypass, родительский SQL-фильтр и ошибочные IDs.

`tests/integration/api/learningAccess.test.ts` использует настоящий Payload REST и PostgreSQL: запрет ID/find/select/depth и Local API, закрытие email enumeration, невозможность смены режима ученику, inherited grant + lesson deny, запись закрытых данных без XP, чтение и PATCH после отзыва, публикация родителей, тема с чужим roadmap, expiry/unique/immutable audit, cleanup и инвалидирование снимка после изменения.

`learningAccessConcurrency.test.ts` приостанавливает реальный REST PATCH после заполнения fallback, позволяет административному API зафиксировать `assigned`/`deny`, затем продолжает старый PATCH. Проверяются обычное изменение профиля, попытка ученика передать `all` и изменение комментария назначения; новое ограничение сохраняется, а аудит содержит фактическое предыдущее состояние. `learningAccessRawPatch.test.ts` отдельно проверяет разделение коллекций/IDs/запросов, `undefined` и bulk-update.

Дополнительные сценарии останавливают реальный SDK login после чтения исходного User, либо logout перед его полной записью. Администратор фиксирует отзыв режима/понижение роли; затем старая операция SDK завершается. Проверяется, что даже восстановленное SDK зеркальное `all`/`admin` в Users не открывает урок, чужой профиль или административный API. Пароль, timestamps и XP проходят реальные совместимые REST проверки.

## Долгие сессии и защита от гонок SDK

JWT/cookie сохраняются на 30 дней. Два параллельных входа сохраняют обе активные сессии: первая запись SDK под блокировкой пользовательской строки объединяет текущие и входящие SID, удаляя истёкшие и выбирая более поздний срок для одного SID. Это применяется к успешному login; штатная защита от brute force не объединяет SID, а сохраняет своё намеренное удаление недавних сессий. Её атомарные счётчики `loginAttempts`/`lockUntil` не перезаписываются устаревшим полным снимком.

Внешний transaction wrapper вокруг проверки пароля не используется: SDK намеренно обновляет счётчик неправильных входов на другом соединении, и преждевременный `users FOR UPDATE` вызвал бы взаимную блокировку. Перед подписанием успешного JWT `beforeLogin` сравнивает текущие hash/salt с проверенной SDK копией; конкурентная смена пароля даёт 401 и откат новой сессии, сохраняя новый пароль. Reset/refresh берут строку пользователя в уже открытой SDK транзакции перед чтением; refresh повторно проверяет наличие своего активного SID и возвращает 403 после конкурентного выхода.

`auth-session-revocations` хранит только SHA-256 SID, пользователя и срок отзыва; сырой SID/JWT не сохраняется. Прямые CRUD/read запрещены, внутренние хуки имеют отдельную capability. Logout записывает отзыв своего SID в той же транзакции, затем SDK убирает сессию. `?allSessions=true` отзывает все текущие SID и SID самого аутентифицированного запроса; низкоуровневый внутренний `logoutOperation` с `allSessions` должен дополнительно передавать `context.revokeAllAuthSessions: true`, поскольку SDK не передаёт этот аргумент hook.

После чтения Users активные отзывы фильтруют `sessions` **до** JWT Authentication. Поэтому отложенный вход другого устройства не восстанавливает уже отозванный токен, даже если SDK вернул прежний SID в Users. Другой действительный SID остаётся рабочим. Срок отзыва покрывает максимальную жизнь токена плюс день запаса; истёкшие записи пользователя очищаются при его последующем logout. Предикат срока индексирован, запросы SID ограничены батчами по 500; активные отзывы никогда не отбрасываются ради ограничения массива.

`isActive: false` теперь означает отключение аккаунта: новый вход возвращает 401, существующий JWT не проходит проверку сессии, пользователь также скрыт из лидерборда. Это расширяет прежнюю семантику поля, которое раньше влияло только на лидерборд. Админская форма описывает блокировку явно; существующие неактивные пользователи требуют проверки перед выкатом.

Запуск интеграционных проверок — только в одноразовой локальной БД, согласованно с другими задачами. Тесты не создают учеников и назначения на проде.

В режиме скрытого каталога описания родительских курсов, разделов и узлов не выдаются ученику: общий текст может перечислять неназначенные материалы. Названия доступных родителей остаются для навигации. Закладки и уведомления проверяют текущий доступ; закрытое уведомление отображается без названия материала, а ожидающий пуш отменяется. Уже выданные личные сертификаты и история начисленных баллов сохраняются.

Новые ученики получают «только назначенное» для курсов, скрытый каталог и тренажёр по назначениям. Миграция сохраняет прежнюю видимость каталога и доступ к тренажёру существующих аккаунтов; администратор меняет их отдельно.
