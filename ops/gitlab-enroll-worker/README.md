# Исполнитель зачислений в VM GitLab

Кнопка «Зачислить» в заявке на буткемп (CMS LMS) сразу заводит учётку LMS и открывает
курс методичек, а учётку и проект в GitLab создаёт этот исполнитель. Он живёт в VM
`gitlab`, раз в 15 секунд забирает задание из LMS (`POST /api/internal/bootcamp-enrollments/claim`)
и выполняет шаги через локальный API GitLab от имени root, отчитываясь после каждого.
Токен root VM не покидает; LMS не может обратиться к GitLab сама.

Шаги те же, что у `npm run students:add` репозитория bootcamp/content: учётка с письмом
для пароля, проект `<поток>/<логин>` форком репозитория курса с разорванной связью,
защита `main`, роль Developer. Репозиторий курса и проект проверки берутся из программы
буткемпа заявки (CMS, Буткемпы, Программы буткемпов) и приходят в задании
(`courseProject`, `gradingProject`); у Node.js это `bootcamp/course` и `bootcamp-staff/grading`.
Группа потока должна быть в `GRADER_GROUPS` проекта проверки, иначе шаг проверки потока падает. Сверх того исполнитель ставит в проект вебхук
`/api/bootcamp/gitlab-events`: MR, CI и комментарии ученика приходят наставнику в Telegram.
Раз в 5 минут он проверяет, вошли ли недавно зачисленные в GitLab впервые.

При возврате буткемпа или закрытии доступа к менторству исполнитель удаляет прямое
членство ученика в соответствующем проекте и проверяет эффективный доступ. Учётка
и проекты другого продукта остаются доступны, а история GitLab сохраняется.

При получении заданий массового буткемпа эта версия сообщает LMS
`x-lms-enrollment-protocol: 2`. При покупке еще одного курса LMS может
передать ранее подтвержденный `gitlabUserId` этого ученика. Исполнитель сверяет
ID, основную подтвержденную почту и состояние личного аккаунта. Ссылка
для смены пароля повторно не отправляется. Каждый курс получает собственный
проект в указанной группе. Для отзыва проверяются сохраненные ID ученика и
проекта, а также полный путь проекта из задания. По возможности обновите
исполнитель до публикации LMS, чтобы задания с повторной покупкой выполнялись сразу.

Если в базе уже появились зачисления с одним логином GitLab в двух группах,
для отката приложения оставьте расширенную схему базы. Прежний уникальный индекс
по одному логину не сможет восстановиться с этими записями. У каждого курса
должны сохраниться собственные покупка, история учебы и проект.

### PostgreSQL в стартовом проекте Node.js

Оба продукта выдают копию текущей `main` проекта `bootcamp/course`. Для задания
с бронями в `check` нужен сервис `postgres:18.6` и переменная
`TEST_POSTGRES_URL`. PostgreSQL работает только в сети конкретного задания.
Обновление шаблона дойдет до новых копий после слияния в GitLab.

Для прежнего шаблона и ранее выданных копий подготовлен
[патч одного файла](node-postgres-ci.patch). Наставник применяет его в новой
ветке свежего клона нужного проекта и открывает обычный запрос на слияние.
В примере `patch_file` - абсолютный путь к патчу в рабочей копии LMS.

```sh
git switch -c ci/course-postgres
git apply --check "$patch_file" && git apply --index "$patch_file"
git diff --cached -- .gitlab-ci.yml
```

Если в `check` уже указаны сервис PostgreSQL и адрес для тестов, исправление
уже действует. Если Git сообщает о конфликте, проверьте текущий CI ученика и
добавьте только недостающие настройки. После проверки изменений и обычного
слияния тесты этапа с бронями должны пройти с ненулевым числом проверок базы.
Для выдачи ученикам достаточно обновить шаблон, перезапуск службы не требуется.

## Менторство

Исполнитель обслуживает отдельную очередь `/api/internal/tutoring-projects/claim`.
LMS ставит выдачу в очередь, когда ученик получает доступ к активному потоку.
Укажите в программе приватную
подгруппу менторства и числовой ID доверенного бота. Для Node.js используется
`nodejs-bootcamp/mentoring-nodejs`: бот потока наследует роль Developer в подгруппе,
а ученики получают роли отдельно в своих проектах. Добавьте точный путь подгруппы
в `GRADER_GROUPS`. Проект ученика создаётся только в приватной группе без
сторонних участников с унаследованным доступом. LMS принимает вердикт
только от указанной учётки. Если очередь менторства разворачивают с нуля,
сначала нужна миграция LMS. При обновлении работающей очереди для автоматической
выдачи с `autoResolveUsername` установите исполнитель до выката LMS.
Он понимает и прежние задания.
Старый исполнитель умеет создать новую учётку, но остановит выдачу, если почта
уже зарегистрирована под другим логином.

Ученику с новой учётной записью GitLab отправляет на почту из LMS ссылку для
выбора пароля. Если аккаунт ранее создан, ученик входит со своим паролем.
В автоматическом режиме исполнитель сверяет точную подтверждённую основную
почту, состояние и тип учётки. Ученик с другим логином сохраняет его;
путь проекта остаётся таким, каким его выдала LMS. При повторной выдаче
сохранённый ID пользователя должен совпасть. При отзыве используются ID
пользователя, ID проекта и его путь. У вручную заданного логина сохраняется
проверка совпадения логина и почты. При ошибке подготовки или недоступной учётке наставник видит
причину в карточке ученика и может повторить выдачу.

## Установка (root в VM gitlab)

```sh
install -m 0755 lms-gitlab-worker.py /usr/local/sbin/lms-gitlab-worker
install -m 0644 lms-gitlab-worker.service /etc/systemd/system/
install -d -m 0700 /etc/lms-gitlab-worker
# Ключ: HMAC-SHA256 от PAYLOAD_SECRET прода по метке lms-bootcamp-enroll-worker-v1,
# 64 шестнадцатеричных знака. Считается в контейнере LMS и сразу пишется сюда, на экран не выводится.
chmod 0600 /etc/lms-gitlab-worker/key
systemctl daemon-reload && systemctl enable --now lms-gitlab-worker
journalctl -u lms-gitlab-worker -f
```

Ключ из Mac по SSH, без вывода значения (`infra/ssh.cfg`):

```sh
ssh -F infra/ssh.cfg vm 'c=$(sudo -n docker ps --format "{{.Names}}" | grep lms-mentor-app | head -1); sudo -n docker exec "$c" node -e "process.stdout.write(require(\"crypto\").createHmac(\"sha256\", process.env.PAYLOAD_SECRET).update(\"lms-bootcamp-enroll-worker-v1\").digest(\"hex\"))"' \
  | ssh -F infra/ssh.cfg gitlab 'sudo install -d -m 0700 /etc/lms-gitlab-worker && sudo tee /etc/lms-gitlab-worker/key >/dev/null && sudo chmod 0600 /etc/lms-gitlab-worker/key'
```

Смена `PAYLOAD_SECRET` меняет ключ исполнителя и токен вебхуков: ключ кладут заново,
а вебхуки проектов обновит повтор зачисления (или правка токена в настройках проекта).

## Если зачисление упало

Причина видна в заявке, в карточке зачисления и в Telegram. После исправления -
«Повторить шаги GitLab» в заявке: сделанные шаги исполнитель пропустит. Брошенное
задание (исполнитель перезапустился посреди работы) LMS отдаёт снова через 10 минут,
после пяти таких попыток помечает ошибкой.
