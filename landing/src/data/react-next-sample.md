## Задача проката

Сотрудник проката сравнивает инструменты перед оформлением брони. Сейчас данные уже доступны на сервере, но первая версия интерфейса должна научиться честно их показывать. На этой неделе список локальный: сетевой слой появится отдельно. Это позволяет увидеть главную работу React без шума асинхронности: из входных данных получить понятную структуру страницы.

Карточка должна объяснять название, категорию, цену за сутки и залог. «Красиво выглядит» недостаточно. Если цена 45000 копеек показана как 45000 рублей, сотрудник сообщит клиенту неправильную стоимость. Если всё сделано из div без заголовков и ссылок, клавиатурная навигация и тесты будут хрупкими. Начинайте с содержания и смысла, затем добавляйте CSS.

## Теория

### Компонент - функция с ответственностью

Компонент получает входные данные и возвращает описание интерфейса. Его удобно выделять, когда у части страницы есть собственный смысл: карточка, список карточек, сообщение об отсутствии результатов. Файл из одной строки не становится хорошей архитектурой только потому, что назван компонентом. С другой стороны, список, форматирование цены и описание каждой карточки в одной большой функции трудно изменять независимо.

Сначала нарисуйте дерево: экран каталога содержит заголовок, сводку и список; список содержит карточки; карточка содержит название и две денежные величины. Обсудите, какие части зависят от предметной области. Универсальный компонент Text не объясняет устройство проката, а Price сообщает, что значение имеет валюту и формат. Обобщение имеет смысл после повторения, которое вы действительно наблюдаете.

### JSX и выражения JavaScript

JSX похож на HTML, но находится внутри JavaScript. В фигурных скобках вычисляется выражение: значение, вызов чистой функции или результат map. Условный оператор решает, какой фрагмент вернуть. Цикл for и if можно использовать до return; вставить инструкцию прямо внутрь фигурных скобок нельзя. Корневой результат может быть обёрнут в семантический элемент или Fragment.

Имя пользовательского компонента начинается с заглавной буквы. Ссылка на функцию и её вызов - разные действия. Для класса в JSX используется className. Значения props передаются строками или выражениями. Не решайте проблемы JSX добавлением dangerouslySetInnerHTML: строка названия инструмента должна оставаться текстом, даже если в ней встретились угловые скобки. Сырой HTML из API не является частью контракта каталога.

### Props и односторонний поток

Props принадлежат вызывающей стороне. Компонент карточки не должен исправлять объект цены или дописывать имя в массив. Если один объект показан в двух местах, такая мутация создаст зависимость от порядка рендера. Локальное форматирование возвращает новую строку, а исходные копейки остаются целыми числами. На этой неделе компонент не изменяет данные вообще; следующий шаг - события, выражающие намерение пользователя.

TypeScript помогает не перепутать string и объект Money. Реальный API возвращает dailyPrice и deposit объектами с amountMinor и currency. Это контракт данных, а не повод импортировать серверные модули в браузер. Между backend и frontend передаётся JSON, поэтому общие типы выводятся из OpenAPI. В учебном локальном наборе используйте ту же форму данных, чтобы позже не переписывать все компоненты при подключении API.

### Чистый рендер

Чистота здесь означает: одинаковые входные данные дают одинаковое описание, а вычисление не меняет внешний мир. Не посылайте запрос и не записывайте в localStorage в теле компонента. Не изменяйте глобальный счётчик, чтобы получить key. React может повторить вычисление, а пользователь от этого не должен получить повторную операцию. Пока вам достаточно чистого преобразования props в JSX.

Сортировка - типичная скрытая мутация. Если список приходит в props, items.sort меняет данные родителя. Для выбранного порядка создайте копию или заранее передайте упорядоченный список. Не добавляйте useMemo для исправления мутации: мемоизация не меняет контракт операции и не делает нечистую функцию чистой.

### Списки и идентичность

Key помогает React сопоставить элемент списка между рендерами. Используйте устойчивый идентификатор данных. Индекс описывает позицию, а не инструмент; при вставке и перестановке позиция может перейти к другому инструменту. Случайное значение на каждом рендере делает идентичность нестабильной. Key нужен самому React и не передаётся компоненту как обычный prop: если нужен id, передайте его отдельно.

На статической неделе неверный key может не проявиться. Специально вставьте карточку в начало и поменяйте порядок. На следующей неделе появится состояние, и такие ошибки станут заметнее. Проверяйте не внутренний номер key, а пользовательское поведение: нужная подпись, правильная ссылка и сохранённый выбор у нужного элемента.

### Цена и семантика

Умножать цену на количество дней сейчас не требуется: на API это делает сервер по правилам брони. Здесь вы только форматируете известную сумму. Для вывода валюты подходит Intl.NumberFormat с явно выбранной локалью и валютой. Деление amountMinor на 100 допустимо при форматировании отображения; оно не должно превращаться в новый источник расчётов и обратных преобразований.

Выберите заголовки последовательно: один h1 страницы, h2 секции или карточки по структуре, ссылка с названием инструмента. Интерактивная карточка не должна содержать кнопку внутри ссылки на всю карточку. Для категории подходит текст, для набора свойств - dl. Пустой каталог нуждается в сообщении, а не в пустом прямоугольнике.

## Разобранные примеры

Пример показывает список проверок защитного снаряжения. Это соседний экран, а не решение каталога. Данные передаются целиком через props. Компонент не запоминает собственную копию conditions и не меняет checked. Одна ветвь отвечает за пустое состояние, другая - за семантический список. У строки стабильный id, её статус показан словами.

Раздел имеет доступное имя через aria-label. Тест находит именно этот раздел и проверяет его содержимое через within. Такой тест переживёт смену className и оформление, но обнаружит исчезнувший смысл. Обратите внимание: name строки и title секции являются текстом, не HTML. Вставьте в label символы < и > и убедитесь, что они не превращаются в исполняемую разметку.

```tsx title="examples/week-01/ConditionList.tsx"
type Condition = {
  id: string
  label: string
  checked: boolean
}

type Props = {
  title: string
  conditions: readonly Condition[]
}

export function ConditionList({ title, conditions }: Props) {
  return (
    <section aria-label={title}>
      <h2>{title}</h2>
      {conditions.length === 0 ? (
        <p>Проверки пока не добавлены</p>
      ) : (
        <ul>
          {conditions.map((condition) => (
            <li key={condition.id}>
              <span>{condition.label}</span>
              <span>{condition.checked ? 'Проверено' : 'Нужна проверка'}</span>
            </li>
          ))}
        </ul>
      )}
    </section>
  )
}
```

Файл теста лежит рядом: `ConditionList.test.tsx`.
Запустите проверки из корня учебного проекта:

```sh
pnpm check
```

Проверки примера проверяют наблюдаемое поведение. Измените один значимый случай
и убедитесь, что ошибочная версия обнаруживается. Затем верните рабочую версию.
Зелёный тест не доказывает правильность любого возможного поведения; его границу
определяют проверенные входы и требование, которое он выражает.
