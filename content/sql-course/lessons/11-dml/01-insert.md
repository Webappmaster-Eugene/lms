Всё, что мы делали до сих пор, только читало данные. Теперь начинаем их менять. Команды, которые изменяют данные, делятся на три: INSERT добавляет строки, UPDATE меняет существующие, DELETE удаляет. Вместе их называют DML, языком манипулирования данными. Начнём с INSERT.

Каждый пример ниже выполняется на свежей копии данных, поэтому изменение и проверочный SELECT стоят в одном блоке. В своей базе вы сначала выполняете INSERT, а проверяете отдельным запросом.

## Одна строка

После INSERT INTO идёт имя таблицы, в скобках список столбцов, затем слово VALUES и в скобках значения в том же порядке:

```sql run=library
INSERT INTO authors (id, full_name, country, birth_year)
VALUES (7, 'Иван Бунин', 'Россия', 1870);

SELECT * FROM authors ORDER BY id;
```

Строки текста пишутся в одинарных кавычках, числа без кавычек, пустое значение это слово NULL. Если внутри текста есть апостроф, его удваивают: `'O''Brien'`.

Список столбцов можно не писать. Тогда значения идут в порядке, в котором столбцы объявлены в таблице, и их должно быть ровно столько, сколько столбцов:

```sql run=library
INSERT INTO authors VALUES (8, 'Иван Гончаров', 'Россия', 1812);

SELECT * FROM authors WHERE id >= 7 ORDER BY id;
```

Так писать допустимо в учебных примерах, но в рабочем коде список столбцов лучше оставлять. Если позже в таблицу добавят столбец, запрос без списка начнёт падать, а запрос со списком продолжит работать.

## Пропущенные столбцы и DEFAULT

Столбец, которого нет в списке, получает значение по умолчанию. Оно записано в определении таблицы после слова DEFAULT. Если его нет, подставляется NULL, а если столбец объявлен NOT NULL без значения по умолчанию, вставка завершится ошибкой.

Покажем это на небольшой таблице, которую создадим прямо в примере:

```sql run=empty
CREATE TABLE tickets (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  status text NOT NULL DEFAULT 'open',
  assignee text
);

INSERT INTO tickets (title) VALUES ('Не открывается страница');
INSERT INTO tickets (title, status) VALUES ('Опечатка в письме', 'closed');

SELECT * FROM tickets ORDER BY id;
```

Номер задачи создал сам столбец-счётчик. Статус первой строки взят из DEFAULT, а в `assignee` лежит NULL, потому что значения по умолчанию у него нет. Подробнее о счётчиках и ограничениях будет в разделе о структуре таблиц.

Значение по умолчанию можно запросить явно словом DEFAULT на месте значения. Это удобно, когда запрос собирается из частей:

```sql run=empty
CREATE TABLE tickets (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  status text NOT NULL DEFAULT 'open'
);

INSERT INTO tickets (title, status) VALUES ('Сломалась кнопка', DEFAULT);

SELECT * FROM tickets;
```

Строка, в которой для всех столбцов нужны значения по умолчанию, пишется так: `INSERT INTO tickets DEFAULT VALUES`.

## Несколько строк

Строки можно перечислить через запятую в одном запросе:

```sql run=shop
INSERT INTO categories (id, title)
VALUES (10, 'Игры'), (11, 'Канцелярия'), (12, 'Дом');

SELECT * FROM categories ORDER BY id;
```

Это быстрее, чем три отдельных запроса: меньше обращений к базе, и запрос применяется целиком. Если одна из строк не пройдёт проверки, не добавится ни одна.

## Выражения и подзапросы в значениях

На месте значения можно писать выражение или скалярный подзапрос, то есть запрос, который возвращает одно значение:

```sql run=company
INSERT INTO employees (id, full_name, department_id, position, salary, hire_date, birth_date)
VALUES (
  20, 'Кирилл Рогов', 4, 'Стажёр',
  (SELECT min(salary) FROM employees),
  '2026-05-04', '2005-03-09'
);

SELECT id, full_name, salary FROM employees WHERE id >= 11 ORDER BY id;
```

Подзапрос выполняется до вставки, поэтому новая строка в минимум не попадает. Даты записаны текстом: PostgreSQL сам приводит строку формата `ГГГГ-ММ-ДД` к типу date.

## Что бывает при ошибках

Ограничения таблицы проверяются при каждой вставке. Повтор первичного ключа:

```sql run=library error
INSERT INTO authors (id, full_name) VALUES (1, 'Дубль Толстого');
```

Ссылка на несуществующую строку, нарушающая внешний ключ:

```sql run=library error
INSERT INTO books (id, title, author_id) VALUES (20, 'Книга без автора', 99);
```

Пустое значение в столбце NOT NULL:

```sql run=library error
INSERT INTO authors (id, country) VALUES (9, 'Россия');
```

Во всех трёх случаях запрос не оставляет после себя ничего: ни одной новой строки.

Порядок вставки в связанные таблицы имеет значение. Заказ ссылается на покупателя, поэтому покупателя нужно добавить раньше:

```sql run=shop
INSERT INTO customers (id, full_name, city, email, registered_on)
VALUES (20, 'Марина Орлова', 'Тула', 'marina@mail.example', '2026-05-01');

INSERT INTO orders (id, customer_id, ordered_at, status)
VALUES (20, 20, '2026-05-02 09:00:00', 'new');

SELECT o.id, c.full_name, o.status
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.id = 20;
```

## RETURNING: получить добавленную строку

Часто после вставки нужны значения, которые создала база: номер строки из счётчика или значение по умолчанию. В PostgreSQL для этого есть RETURNING в конце запроса:

```sql run=empty
CREATE TABLE tickets (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  status text NOT NULL DEFAULT 'open'
);

INSERT INTO tickets (title) VALUES ('Новая заявка') RETURNING id, status;
```

Результат выглядит как у SELECT, но это ответ INSERT: строка уже записана. RETURNING принимает те же выражения, что и список SELECT, включая `*` и псевдонимы. Для нескольких вставленных строк вернётся несколько строк.

Отдельного SELECT после вставки не нужно, и нет риска, что между ними кто-то вставит свою строку. В MySQL RETURNING для INSERT нет: номер новой строки получают функцией `LAST_INSERT_ID()`.

## Отличие от MySQL в мелочах

В MySQL текст можно писать и в одинарных, и в двойных кавычках. В PostgreSQL двойные кавычки обозначают имя объекта, поэтому текст всегда в одинарных. Столбец-счётчик в MySQL называется AUTO_INCREMENT, в PostgreSQL используется `GENERATED ... AS IDENTITY` или тип `serial`.
