Каждое значение в PostgreSQL имеет тип: число, текст, дата, логическое значение. База строго следит за ними, и там, где типы не сходятся, одним значением нельзя подменить другое. Приведение типов - явное превращение значения из одного типа в другой. Есть две записи, и они делают одно и то же.

```sql run=empty
SELECT CAST('42' AS integer) AS by_cast, '42'::integer AS by_operator;
```

`CAST(значение AS тип)` соответствует стандарту SQL и понятна в любой базе. Оператор `::` - сокращение, принятое в PostgreSQL, и на практике встречается чаще. Он связывает теснее арифметики и сравнений: `a + b::text` приводит к тексту только `b`. Когда выражение сложное, берите его в скобки: `(a + b)::text`.

## Текст в число

Данные из файлов, форм и внешних систем часто приходят текстом. Чтобы с ними считать, нужно приведение:

```sql run=empty
SELECT
  '12'::integer + 5 AS int_sum,
  '199.90'::numeric * 3 AS money,
  '1e3'::numeric AS scientific;
```

Если строка не похожа на число, PostgreSQL останавливает весь запрос с ошибкой:

```sql run=empty error
SELECT 'abc'::integer;
```

Для целого типа не годятся даже пустая строка и число с точкой: `''::integer` и `'7.5'::integer` тоже ошибки. Одна неудачная строка в миллионе роняет весь запрос. Поэтому сначала отсекают мусор в WHERE, а потом приводят остальное. Для проверки пригодится регулярное выражение:

```sql run=empty
SELECT raw, raw::integer AS qty
FROM (VALUES ('12'), ('abc'), ('7'), ('')) AS t(raw)
WHERE raw ~ '^[0-9]+$'
ORDER BY qty;
```

Выражение `^[0-9]+$` пропускает только строки целиком из цифр. Фильтр в WHERE выполняется до вычисления списка столбцов, поэтому `'abc'` до приведения не доходит. Но в сложных запросах порядок проверки условий не гарантируется, а в PostgreSQL 16 и новее есть и готовая функция `pg_input_is_valid('abc', 'integer')`, которая отвечает на вопрос «приведётся ли значение» без ошибки.

```sql run=empty
SELECT raw, pg_input_is_valid(raw, 'integer') AS ok
FROM (VALUES ('12'), ('abc'), ('7.5'), (' 8 ')) AS t(raw)
ORDER BY raw;
```

В MySQL приведение строки к числу молча берёт цифры с начала и не падает: `'12abc' + 0` даёт 12. В PostgreSQL так не бывает, и это защищает от скрытых искажений данных.

## Число в текст

Обратное приведение нужно для склейки с текстом и для форматирования. Оператор `||` склеивает только строки, число перед ним приводят к тексту:

```sql run=shop
SELECT title || ': ' || price::text AS label
FROM products
ORDER BY id
LIMIT 4;
```

Тип numeric(10, 2) хранит два знака после точки, поэтому цена 990 выводится как `990.00`. Другой формат даёт `to_char`, о нём будет в разделе про даты и форматы. Функция `concat` умеет склеивать значения любого типа без приведения, но она пропускает NULL, а `||` с NULL даёт NULL.

## Дробное в целое

Приведение numeric или double precision к integer округляет, а не отбрасывает дробь:

```sql run=empty
SELECT
  2.4::integer AS down,
  2.5::integer AS numeric_half,
  3.5::integer AS also_up,
  2.5::double precision::integer AS double_half,
  TRUNC(2.9)::integer AS cut;
```

Для numeric половинка идёт от нуля (2,5 даёт 3), для double precision - к ближайшему чётному (2,5 даёт 2). Если нужно отбросить дробь, используйте `TRUNC` или `FLOOR`, а потом приводите. Если дробь нужна, приводите в обратную сторону: целое к numeric.

## Целое в дробное

Это решение проблемы целочисленного деления. Достаточно привести один из операндов:

```sql run=library
SELECT
  title,
  pages / 100 AS cut_off,
  pages::numeric / 100 AS exact,
  ROUND(pages::numeric / 100, 1) AS hundreds
FROM books
ORDER BY id
LIMIT 5;
```

Колонка `cut_off` хранит целую часть, а `exact` - точную дробь. Приведение к numeric предпочтительнее приведения к double precision, потому что численные ошибки в десятичных дробях не накапливаются.

Приведение к узкому типу проверяет размер числа: `300::smallint` проходит, а `100000::smallint` вызывает ошибку, потому что число не помещается в тип.

## Текст в дату

Строку формата `ГГГГ-ММ-ДД` PostgreSQL приводит к дате без дополнительных подсказок, и после этого с ней можно сравнивать, складывать и сортировать:

```sql run=empty
SELECT
  '2026-03-05'::date AS day,
  '2026-03-05'::date + 30 AS plus_30_days,
  '2026-03-05 14:30:00'::timestamp AS moment;
```

Невозможные даты и непонятные форматы приводят к ошибке:

```sql run=empty error
SELECT '2026-13-45'::date;
```

Для дат в чужих форматах (`15.03.2026`, `03/15/2026`) есть функция `to_date(текст, шаблон)`. Она подробно разобрана в разделе про даты.

## Логические значения

Сравнения возвращают boolean, и это значение можно привести к числу: true даёт 1, false даёт 0. Это удобный способ превратить условие в флаг:

```sql run=shop
SELECT title, stock, (stock > 0)::integer AS in_stock
FROM products
ORDER BY id;
```

Скобки вокруг сравнения нужны, чтобы `::` применился ко всему выражению, а не к последнему операнду. Обратное тоже работает: `1::boolean` даёт true, `0::boolean` - false, а строки `'true'`, `'t'`, `'yes'`, `'1'` приводятся к true.

## Приведение в литералах

Рядом с литералом можно писать тип: `DATE '2026-03-05'`, `INTERVAL '1 day'`, `NUMERIC '1.5'`. Это то же приведение, только в другой записи. Такая форма удобна в условиях по датам. Задачи курса часто используют именно её для фиксации «сегодняшней» даты.
