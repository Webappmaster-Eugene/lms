В базе одновременно работают сотни транзакций. Изоляция определяет, насколько каждая из них видит изменения соседей. Полная изоляция безопасна, но замедляет работу, поэтому стандарт SQL описывает четыре уровня, от слабого к строгому.

Примеры в тренажёре идут через одно соединение, и одновременную работу двух сессий в них показать нельзя. Сценарии ниже записаны как два окна psql: действия идут по порядку времени, и в комментарии указано, какое окно что делает. Эти блоки не запускаются.

## Аномалии

Каждый уровень защищает от определённого набора неприятных эффектов. Они называются аномалиями.

Грязное чтение: транзакция видит данные другой, которая ещё не зафиксирована и потом может откатиться. В PostgreSQL грязного чтения не бывает ни на одном уровне.

Неповторяющееся чтение: транзакция дважды читает одну строку и получает разные значения, потому что между чтениями другая транзакция изменила её и зафиксировала.

```sql
-- окно A
BEGIN;
SELECT balance FROM accounts WHERE id = 1;   -- 1000

-- окно B
UPDATE accounts SET balance = 1500 WHERE id = 1;   -- автофиксация

-- окно A
SELECT balance FROM accounts WHERE id = 1;   -- 1500: то же чтение, другой ответ
COMMIT;
```

Фантомное чтение: повторный запрос с условием возвращает другой набор строк, потому что другая транзакция добавила или удалила подходящие строки.

```sql
-- окно A
BEGIN;
SELECT count(*) FROM orders WHERE status = 'new';   -- 2

-- окно B
INSERT INTO orders (id, customer_id, ordered_at, status) VALUES (9, 1, '2026-05-01 10:00:00', 'new');

-- окно A
SELECT count(*) FROM orders WHERE status = 'new';   -- 3: появилась новая строка
COMMIT;
```

Потерянное обновление: две транзакции читают одно значение, обе считают новое и записывают, и результат второй затирает результат первой. Если выполнять `UPDATE accounts SET balance = balance + 100` одним запросом, база сама блокирует строку и ошибки не будет. Проблема возникает, когда значение читают в приложение, считают там и записывают обратно.

Аномалия сериализации: каждая транзакция по отдельности корректна, но их общий результат невозможен при любом последовательном порядке. Классический пример: правило «в дежурстве должен остаться хотя бы один врач». Два врача одновременно проверяют, что второй ещё на смене, и оба уходят.

## Четыре уровня

READ UNCOMMITTED допускает грязное чтение по стандарту. В PostgreSQL этот уровень ведёт себя как READ COMMITTED: грязных чтений тут нет вообще.

READ COMMITTED: каждый запрос видит данные, зафиксированные к моменту его начала. Поэтому неповторяющееся и фантомное чтение возможны. Это уровень по умолчанию в PostgreSQL.

REPEATABLE READ: транзакция работает с моментальным снимком данных на момент первого запроса и больше не видит чужих изменений. В PostgreSQL этот уровень защищает и от фантомов, строже стандарта. Если транзакция пытается изменить строку, которую уже изменила и зафиксировала другая, база прерывает её ошибкой `could not serialize access due to concurrent update`, и приложение должно повторить транзакцию с начала.

SERIALIZABLE: результат равен последовательному выполнению транзакций. PostgreSQL обнаруживает опасные цепочки зависимостей и прерывает одну из транзакций с кодом ошибки 40001. Приложение обязано быть готово повторить транзакцию.

В MySQL с InnoDB по умолчанию REPEATABLE READ, и он ведёт себя иначе: читает по снимку, но обновления видят последние данные, а фантомы закрываются блокировками диапазонов.

## Как задать уровень

Уровень задаётся при начале транзакции или командой SET TRANSACTION, но до первого запроса внутри неё. Текущий уровень показывает SHOW:

```sql run=empty
BEGIN ISOLATION LEVEL REPEATABLE READ;
SHOW transaction_isolation;
COMMIT;
```

Вариант с отдельной командой:

```sql run=empty
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SHOW transaction_isolation;
COMMIT;
```

Если SET TRANSACTION выполнить после запроса, PostgreSQL ответит ошибкой: уровень уже зафиксирован.

```sql run=empty error
BEGIN;
SELECT 1;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

Уровень по умолчанию для всех транзакций сессии меняют командой `SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL ...` или настройкой `default_transaction_isolation`. В MySQL для этого пишут `SET SESSION TRANSACTION ISOLATION LEVEL ...`.

## Режимы READ ONLY и DEFERRABLE

Вместе с уровнем можно указать режим. READ ONLY запрещает любую запись внутри транзакции, это защита для отчётов. READ WRITE разрешает запись и действует по умолчанию. Для SERIALIZABLE READ ONLY есть дополнительный режим DEFERRABLE: транзакция ждёт безопасного снимка и потом работает без риска быть прерванной.

```sql run=company error
BEGIN READ ONLY;
UPDATE employees SET salary = 0 WHERE id = 1;
```

## Что выбрать

На READ COMMITTED пишут большинство приложений: он быстрый и достаточно безопасен, если сложные правила защищены ограничениями и блокировками. REPEATABLE READ подходит отчётам, которым нужна согласованная картина данных на один момент времени, например несколько запросов подряд по одному снимку. SERIALIZABLE выбирают, когда логику сложно защитить иначе, и берут на себя повторы после 40001.

Показательный пример для отчёта. Одна транзакция REPEATABLE READ видит один и тот же набор данных, даже если параллельно оформляют заказы:

```sql
-- окно A
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SELECT count(*) FROM orders;               -- 8
SELECT sum(quantity) FROM order_items;     -- итоги согласованы между собой

-- окно B
INSERT INTO orders (id, customer_id, ordered_at, status) VALUES (9, 1, '2026-05-01 10:00:00', 'new');

-- окно A
SELECT count(*) FROM orders;               -- по-прежнему 8
COMMIT;
```

Без этого уровня итоги двух запросов могли бы относиться к разным моментам, и цифры не сошлись бы.

## Повтор после отказа

Ошибки 40001 (serialization_failure) и 40P01 (deadlock_detected) это не сбой, а обычное поведение на строгих уровнях. Правило для приложения: перехватить такую ошибку, выполнить ROLLBACK и повторить всю транзакцию с BEGIN, ограничив число попыток. Повторять только последний запрос нельзя: снимок данных уже устарел.
