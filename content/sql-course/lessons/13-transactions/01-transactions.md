Перевод денег между счетами состоит минимум из двух запросов: с одного счёта списать, на другой зачислить. Если база упадёт между ними, деньги исчезнут. Транзакция решает эту задачу: это группа запросов, которая выполняется как одно целое. Либо применяются все изменения, либо ни одного.

## Три команды

Транзакцию начинает BEGIN, зафиксировать её (сделать изменения постоянными и видимыми другим) можно командой COMMIT, а отменить все изменения с момента BEGIN - командой ROLLBACK. В стандарте SQL и в MySQL вместо BEGIN чаще пишут START TRANSACTION, PostgreSQL понимает оба варианта.

В примерах ниже таблица создаётся тут же, потому что такие примеры проверяют итоговое состояние данных:

```sql run=empty
CREATE TABLE accounts (
  id integer PRIMARY KEY,
  owner text NOT NULL,
  balance numeric(12, 2) NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 'Анна', 10000), (2, 'Борис', 5000);

BEGIN;
UPDATE accounts SET balance = balance - 2000 WHERE id = 1;
UPDATE accounts SET balance = balance + 2000 WHERE id = 2;
COMMIT;

SELECT * FROM accounts ORDER BY id;
```

Пока транзакция не зафиксирована, другие сессии видят старые значения. После COMMIT оба изменения появляются у всех одновременно.

Теперь отмена. Изменение сделано и отменено, а проверка идёт после:

```sql run=company
BEGIN;
UPDATE employees SET salary = 0;
ROLLBACK;

SELECT id, full_name, salary FROM employees ORDER BY id LIMIT 3;
```

Внутри транзакции после UPDATE все зарплаты были нулевыми, но ROLLBACK вернул прежние значения. Это страховка для рискованных изменений: выполните UPDATE или DELETE внутри BEGIN, посмотрите результат запросом SELECT и только потом решайте, что делать, COMMIT или ROLLBACK.

## Без BEGIN

Если BEGIN не писать, PostgreSQL работает в режиме автофиксации: каждый отдельный запрос сам по себе транзакция и фиксируется сразу после выполнения. Поэтому UPDATE, который вы запустили в одиночку, нельзя отменить командой ROLLBACK: транзакция уже закончилась.

В MySQL похожий режим управляется переменной `autocommit`. А DDL-команды вроде CREATE TABLE там фиксируют транзакцию неявно. В PostgreSQL структура таблиц тоже меняется транзакционно: CREATE TABLE или ALTER TABLE внутри BEGIN можно откатить.

### Как это устроено в тренажёре

Тренажёр отправляет весь ваш код базе одним запросом, как это делает `psql -c` или драйвер, которому передали несколько команд через точку с запятой. У такого запроса свои правила. Без BEGIN все команды в нём выполняются одной общей транзакцией: если упала третья, первые две тоже отменяются. Если в коде есть BEGIN, команды до него входят в ту же транзакцию, что и команды после, поэтому ROLLBACK в конце отменит и их. Транзакцию, которую вы открыли и не закрыли, база отменяет после выполнения, как при отключении клиента: проверка увидит данные без ваших изменений. Поэтому в задачах на транзакции начинайте код с BEGIN и заканчивайте COMMIT или ROLLBACK.

## ACID простыми словами

Надёжность транзакций описывают четырьмя свойствами, из первых букв которых получилось слово ACID.

Atomicity, атомарность: транзакция выполняется целиком или не выполняется вовсе. Промежуточного состояния «списано, но не зачислено» наружу не попадает.

Consistency, согласованность: после транзакции все ограничения выполнены. Проверка `balance >= 0`, внешние ключи, уникальные значения никогда не нарушены в зафиксированных данных.

Isolation, изоляция: параллельные транзакции не мешают друг другу так, будто работают по очереди. Насколько именно, зависит от уровня изоляции, о нём отдельный урок.

Durability, долговечность: после COMMIT изменения не пропадут, даже если сервер сразу упадёт. База записывает их в журнал на диск до подтверждения.

## Ошибка внутри транзакции

В PostgreSQL ошибка в любом запросе переводит транзакцию в состояние aborted, то есть прерванное. После этого она принимает только ROLLBACK, любые другие команды отвергаются:

```sql run=empty error
CREATE TABLE accounts (
  id integer PRIMARY KEY,
  owner text NOT NULL,
  balance numeric(12, 2) NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 'Анна', 100), (2, 'Борис', 5000);

BEGIN;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
COMMIT;
```

Баланс Анны стал бы отрицательным, проверка не прошла, и запрос завершился ошибкой. В psql, где команды вводят по одной, ответы сервера выглядели бы так (после ошибки добавлен ещё один SELECT, чтобы показать состояние транзакции):

```text
BEGIN;                                                -> BEGIN
UPDATE accounts SET balance = balance + 500 WHERE id = 2;  -> UPDATE 1
UPDATE accounts SET balance = balance - 500 WHERE id = 1;  -> ERROR: new row for relation "accounts" violates check constraint "accounts_balance_check"
SELECT * FROM accounts;                               -> ERROR: current transaction is aborted, commands ignored until end of transaction block
COMMIT;                                               -> ROLLBACK
```

На последней строке видно: даже если написать COMMIT, база ответит ROLLBACK, потому что зафиксировать прерванную транзакцию нельзя. Первое зачисление Борису тоже отменено. Это сильная сторона транзакции: ни одного «хвоста» не остаётся.

Приложения обычно ловят ошибку, выполняют ROLLBACK и сообщают пользователю. Если нужно продолжить транзакцию после ошибки, используют точки сохранения, они в следующем уроке.

## Что внутри транзакции видно

Транзакция видит собственные изменения сразу, не дожидаясь COMMIT:

```sql run=library
BEGIN;
INSERT INTO authors (id, full_name) VALUES (7, 'Иван Бунин');
SELECT count(*) AS inside FROM authors;
ROLLBACK;

SELECT count(*) AS after_rollback FROM authors;
```

Под блоком показан последний результат: после отмены автор не добавлен, в таблице прежние шесть строк. Внутри транзакции первый запрос насчитал бы семь. Для DML-команд из прошлого раздела транзакция работает одинаково: INSERT, UPDATE, DELETE и TRUNCATE откатываются. Исключение в PostgreSQL одно: последовательности и счётчики не откатываются. Номер, который взяла отменённая вставка, остаётся потраченным, поэтому в нумерации бывают пропуски. Это нормально.

## Как коротко держать транзакции

Открытая транзакция держит блокировки изменённых строк до конца, поэтому долгие транзакции мешают другим. Не оставляйте BEGIN открытым на время, пока пользователь думает или пока идёт обращение к другой системе. Собирайте нужные запросы, выполняйте и сразу завершайте.
