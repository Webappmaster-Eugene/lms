Когда две транзакции хотят изменить одну строку, одна должна подождать другую. Эту очередь организуют блокировки. Большую часть работы база делает сама: UPDATE и DELETE блокируют изменяемые строки до конца транзакции. Обычный SELECT не блокирует ничего, читающие и пишущие не мешают друг другу. Но иногда нужно заблокировать строки явно.

## SELECT ... FOR UPDATE

Типичная ошибка выглядит так. Приложение читает остаток, проверяет, что денег хватает, и потом записывает новое значение. Между чтением и записью другая транзакция успевает изменить остаток, и проверка устарела. Лечится блокировкой на этапе чтения:

```sql run=empty
CREATE TABLE accounts (
  id integer PRIMARY KEY,
  owner text NOT NULL,
  balance numeric(12, 2) NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 'Анна', 10000), (2, 'Борис', 5000), (3, 'Вера', 0);

BEGIN;
SELECT balance FROM accounts WHERE id = 2 FOR UPDATE;
UPDATE accounts SET balance = balance + (SELECT balance FROM accounts WHERE id = 2) WHERE id = 3;
UPDATE accounts SET balance = 0 WHERE id = 2;
COMMIT;

SELECT * FROM accounts ORDER BY id;
```

FOR UPDATE работает как UPDATE по отношению к другим: выбранные строки блокируются до конца транзакции. Чужие UPDATE, DELETE и такие же SELECT ... FOR UPDATE этих строк будут ждать. Чтение без блокировки не мешает.

Два окна psql показывают, как это работает на деле:

```sql
-- окно A
BEGIN;
SELECT balance FROM accounts WHERE id = 2 FOR UPDATE;   -- 5000

-- окно B
BEGIN;
UPDATE accounts SET balance = 0 WHERE id = 2;           -- ждёт: строка занята

-- окно A
UPDATE accounts SET balance = balance - 1000 WHERE id = 2;
COMMIT;                                                 -- освободила строку

-- окно B: ожидание закончилось, UPDATE выполнен над значением 4000
COMMIT;
```

Блокировки снимаются автоматически при COMMIT или ROLLBACK. Отдельной команды «разблокировать» нет.

## Режимы блокировки строк

В конце SELECT можно указать один из четырёх режимов, от сильного к слабому.

FOR UPDATE: строка будет изменена или удалена. Блокирует всех остальных, кто захочет менять строку или брать любую блокировку на неё.

FOR NO KEY UPDATE: строка будет изменена, но ключевые столбцы не затрагиваются. Слабее предыдущего: не мешает другим транзакциям вставлять строки, которые ссылаются на эту внешним ключом. Обычный UPDATE берёт именно такую блокировку, если ключ не меняется.

FOR SHARE: строку можно читать и блокировать так же другим, но менять и удалять нельзя. Подходит, когда нужно убедиться, что строка не исчезнет, пока транзакция работает.

FOR KEY SHARE: самый слабый, запрещает только удаление строки и изменение ключа. Его база сама берёт при вставке в таблицу с внешним ключом, чтобы родительская строка не пропала.

Режим FOR SHARE в деле: заблокированные счета нельзя изменить или удалить, пока транзакция не закончится.

```sql run=empty
CREATE TABLE accounts (id integer PRIMARY KEY, owner text NOT NULL, balance numeric NOT NULL);
CREATE TABLE transfers (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  from_id integer NOT NULL REFERENCES accounts (id),
  to_id integer NOT NULL REFERENCES accounts (id),
  amount numeric NOT NULL
);
INSERT INTO accounts VALUES (1, 'Анна', 1000), (4, 'Глеб', 500);

BEGIN;
SELECT id FROM accounts WHERE id IN (1, 4) FOR SHARE;
INSERT INTO transfers (from_id, to_id, amount) VALUES (1, 4, 400);
COMMIT;

SELECT * FROM transfers;
```

В MySQL аналогами служат `SELECT ... FOR UPDATE` (то же самое) и `SELECT ... LOCK IN SHARE MODE` или `FOR SHARE` в современных версиях.

## NOWAIT и SKIP LOCKED

По умолчанию запрос с блокировкой ждёт, пока строка освободится. Это можно изменить двумя словами в конце.

NOWAIT: если строка занята, не ждать, а сразу вернуть ошибку `could not obtain lock on row`.

SKIP LOCKED: пропустить занятые строки и работать с остальными. Это основа очередей заданий: несколько работников берут по заданию, и никто не ждёт соседа.

```sql run=empty
CREATE TABLE jobs (
  id integer PRIMARY KEY,
  payload text NOT NULL,
  status text NOT NULL DEFAULT 'new',
  worker text
);
INSERT INTO jobs (id, payload) VALUES (1, 'письмо'), (2, 'отчёт'), (3, 'копия');

UPDATE jobs
SET status = 'taken', worker = 'w1'
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'new'
  ORDER BY id
  LIMIT 1
  FOR UPDATE SKIP LOCKED
);

SELECT * FROM jobs ORDER BY id;
```

Подзапрос выбирает первое свободное задание и блокирует его. Если параллельно другой работник уже взял задание 1 и не завершил транзакцию, наш подзапрос пропустит его и возьмёт задание 2. Без SKIP LOCKED мы бы ждали, пока он закончит.

Для пачки заданий LIMIT увеличивают, а RETURNING сообщает, что взято:

```sql run=empty
CREATE TABLE jobs (
  id integer PRIMARY KEY,
  payload text NOT NULL,
  status text NOT NULL DEFAULT 'new',
  worker text
);
INSERT INTO jobs (id, payload) VALUES (1, 'письмо'), (2, 'отчёт'), (3, 'копия');

WITH picked AS (
  UPDATE jobs
  SET status = 'taken', worker = 'w1'
  WHERE id IN (
    SELECT id FROM jobs WHERE status = 'new' ORDER BY id LIMIT 2 FOR UPDATE SKIP LOCKED
  )
  RETURNING id, payload
)
SELECT id, payload FROM picked ORDER BY id;
```

ORDER BY в подзапросе нужен: без него выбор заданий был бы непредсказуемым.

## Условная запись одним запросом

Иногда блокировку можно заменить условием в UPDATE. Перевод, который происходит только при достатке денег:

```sql run=empty
CREATE TABLE accounts (
  id integer PRIMARY KEY,
  balance numeric(12, 2) NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 10000), (2, 5000);

WITH debit AS (
  UPDATE accounts SET balance = balance - 8000
  WHERE id = 1 AND balance >= 8000
  RETURNING id
)
UPDATE accounts SET balance = balance + 8000
WHERE id = 2 AND EXISTS (SELECT 1 FROM debit);

SELECT * FROM accounts ORDER BY id;
```

Если денег не хватает, списание не вернёт строку, EXISTS окажется ложным и зачисления не будет. Запрос выполняется одной командой, поэтому между проверкой и записью ничего не вклинивается.

## Блокировка таблицы: LOCK TABLE

Команда LOCK TABLE блокирует таблицу целиком в одном из восьми режимов. На практике нужны два-три.

ACCESS SHARE: его берёт обычный SELECT. Он конфликтует только с самым сильным режимом, ACCESS EXCLUSIVE.

ROW EXCLUSIVE: берут INSERT, UPDATE и DELETE. Разные записывающие транзакции друг другу не мешают, они конфликтуют только на строках.

EXCLUSIVE: запрещает всем, кроме обычных чтений, менять таблицу. Подходит для пакетного пересчёта.

ACCESS EXCLUSIVE: запрещает всё, включая SELECT. Его берут DROP TABLE, TRUNCATE и многие виды ALTER TABLE, поэтому такие команды на нагруженной таблице нужно выполнять осторожно.

```sql run=empty
CREATE TABLE accounts (id integer PRIMARY KEY, balance numeric(12, 2) NOT NULL);
INSERT INTO accounts VALUES (1, 1000), (2, 250);

BEGIN;
LOCK TABLE accounts IN EXCLUSIVE MODE;
UPDATE accounts SET balance = round(balance * 1.02, 2);
COMMIT;

SELECT * FROM accounts ORDER BY id;
```

Блокировка таблицы снимается при завершении транзакции. В MySQL для этого есть пара команд LOCK TABLES и UNLOCK TABLES, и работают они по-другому: блокировка держится на соединении, а не на транзакции. Для типичных задач в PostgreSQL блокировок строк достаточно, и целые таблицы блокируют редко.

## Взаимоблокировка

Если две транзакции ждут друг друга, обе ждали бы вечно. Такая ситуация называется взаимоблокировкой, deadlock.

```sql
-- окно A
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;   -- заблокирован счёт 1

-- окно B
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 2;   -- заблокирован счёт 2

-- окно A
UPDATE accounts SET balance = balance + 100 WHERE id = 2;   -- ждёт окно B

-- окно B
UPDATE accounts SET balance = balance + 100 WHERE id = 1;   -- ждёт окно A: круг замкнулся
-- ERROR: deadlock detected
```

PostgreSQL замечает цикл примерно через секунду (настройка `deadlock_timeout`) и прерывает одну из транзакций ошибкой 40P01. Вторая продолжается. Прерванную транзакцию нужно откатить и выполнить заново.

Как не попадать в тупик. Блокируйте строки в одном и том же порядке: например, всегда сначала счёт с меньшим номером. Делайте транзакции короткими. Блокируйте сразу всё нужное одним запросом SELECT ... ORDER BY id FOR UPDATE. И держите в приложении повтор после ошибки 40P01.

## Кто сейчас кого ждёт

Текущие блокировки видны в системных представлениях `pg_locks` и `pg_stat_activity`. Если запрос завис, ищут сессию, у которой в `pg_stat_activity.wait_event_type` значение Lock, и смотрят, кто держит нужную строку. Функция `pg_blocking_pids(pid)` возвращает номера процессов, которые мешают данному. Завершить мешающую сессию можно командой `pg_terminate_backend(pid)`, но делают это только осознанно: её незавершённые изменения откатятся.
