Запрос на SQL описывает, что нужно получить, а как это сделать, решает сам PostgreSQL. Из многих способов выполнить запрос он выбирает самый дешёвый. Этот выбор называется планом. Команда EXPLAIN показывает план, не выполняя запрос.

## Простой план

```sql run=company
EXPLAIN SELECT * FROM employees WHERE salary > 100000;
```

Первая строка плана - `Seq Scan on employees`. Seq Scan - последовательный просмотр: PostgreSQL читает таблицу целиком и проверяет условие у каждой строки. Условие видно во второй строке плана, `Filter`. В скобках у узла три оценки: `cost` - стоимость в условных единицах (до первой строки и до последней), `rows` - ожидаемое число строк, `width` - средняя ширина строки в байтах.

Стоимость - не время и не секунды. Это внутренняя мера работы, которую планировщик использует, чтобы сравнивать планы между собой. Сравнивать можно планы одного запроса, а числа разных запросов друг с другом не сопоставляют.

Чтобы убрать оценки и оставить только устройство плана, добавляют параметр COSTS OFF:

```sql run=company
EXPLAIN (COSTS OFF) SELECT * FROM employees WHERE salary > 100000;
```

## План из нескольких узлов

Сложный запрос раскладывается на дерево узлов. Читают его от самого вложенного узла к внешнему: отступ показывает вложенность, а стрелка `->` отмечает узел-потомок.

```sql run=company
EXPLAIN (COSTS OFF)
SELECT d.name, count(*)
FROM employees e
JOIN departments d ON d.id = e.department_id
GROUP BY d.name
ORDER BY d.name;
```

Внизу плана просмотры таблиц, над ними соединение (Hash Join или Nested Loop), над соединением группировка (HashAggregate), наверху сортировка (Sort). Каждый узел берёт строки у нижнего и передаёт верхнему. Если вы видите узел, который ожидали, например Sort, а он делает много лишней работы, это место для оптимизации.

## Seq Scan и Index Scan

Если у столбца в условии есть индекс, планировщик может пойти по нему: Index Scan находит нужные строки по индексу и читает только их. Но выбирает он по стоимости, а не из принципа. Таблица из тысячи строк и условие на одно значение:

```sql run=empty
CREATE TABLE numbers AS SELECT g AS n FROM generate_series(1, 1000) AS g;
CREATE INDEX idx_numbers_n ON numbers (n);
ANALYZE numbers;
EXPLAIN (COSTS OFF) SELECT * FROM numbers WHERE n = 500;
```

Здесь выбран Index Only Scan: нужное значение целиком лежит в индексе, и в таблицу заглядывать не приходится. Одну запись из тысячи по индексу искать дешевле, чем просматривать таблицу. А вот запрос, который выбирает почти все строки, пойдёт по таблице:

```sql run=empty
CREATE TABLE numbers AS SELECT g AS n FROM generate_series(1, 1000) AS g;
CREATE INDEX idx_numbers_n ON numbers (n);
ANALYZE numbers;
EXPLAIN (COSTS OFF) SELECT * FROM numbers WHERE n > 10;
```

Условие `n > 10` пропускает 99 процентов таблицы, и читать её подряд быстрее, чем прыгать по индексу.

Узлы одной группы: Seq Scan читает всю таблицу, Index Scan идёт по индексу и затем за строкой в таблицу, Index Only Scan берёт всё из индекса, Bitmap Heap Scan собирает номера строк по индексу и читает таблицу страницами.

## EXPLAIN ANALYZE

Простой EXPLAIN даёт оценку. Параметр ANALYZE действительно выполняет запрос и добавляет фактические значения: число строк и время. Это позволяет сравнить, насколько оценка отличалась от жизни.

Выполнение настоящее, поэтому EXPLAIN ANALYZE для INSERT, UPDATE и DELETE изменит данные. Если нужно измерить такую команду, её выполняют внутри транзакции и откатывают. Время работы в примерах урока не показано, потому что оно каждый раз разное. А вот форма с фактическим числом строк без времени детерминирована:

```sql run=company
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT * FROM employees WHERE salary > 100000;
```

В скобке узла теперь стоит `actual rows=...` - сколько строк действительно вернул узел (начиная с PostgreSQL 18 число записано как 8.00, раньше было 8), а строка `Rows Removed by Filter` показывает, сколько отброшено. Если фактическое число сильно отличается от ожидаемого `rows`, у планировщика устаревшая статистика, и план может оказаться плохим. На своём сервере вы увидите ещё `actual time` и `Execution Time`:

```sql
EXPLAIN (ANALYZE) SELECT * FROM employees WHERE salary > 100000;
```

Эта команда выведет те же узлы, но с затраченным временем в миллисекундах для каждого узла и общим временем запроса. Числа будут меняться от запуска к запуску.

## Откуда берутся оценки

Планировщик не пересчитывает строки каждый раз. Он пользуется статистикой, которую собирает команда ANALYZE (и автоматическая очистка autovacuum). Число строк таблицы хранится в `pg_class.reltuples`:

```sql run=company
ANALYZE employees;
SELECT relname, reltuples::integer AS estimated_rows FROM pg_class WHERE relname = 'employees';
```

Подробности по столбцам лежат в представлении `pg_stats`: доля пустых значений, число различных значений, самые частые значения.

```sql run=company
ANALYZE employees;
SELECT attname, null_frac, n_distinct
FROM pg_stats
WHERE schemaname = 'public' AND tablename = 'employees' AND null_frac > 0
ORDER BY attname;
```

`null_frac` - доля пустых значений от 0 до 1. `n_distinct` - число различных значений. Положительное число означает сами значения, отрицательное - долю от числа строк со знаком минус, и -1 значит, что все значения разные. По этим цифрам планировщик решает, сколько строк вернёт условие, и значит, выбирать ли индекс. После массовой загрузки данных ANALYZE запускают вручную, чтобы планы не опирались на старую картину.

## Что запомнить

EXPLAIN показывает план, EXPLAIN ANALYZE выполняет запрос и сверяет оценку с действительностью. Планы читают снизу вверх. Seq Scan - просмотр всей таблицы, Index Scan - по индексу. План зависит от статистики, а статистику обновляет ANALYZE.
