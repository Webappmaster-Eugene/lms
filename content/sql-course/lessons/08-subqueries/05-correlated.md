Обычный подзапрос выполняется один раз и ничего не знает о внешнем запросе. Коррелированный подзапрос устроен иначе: он ссылается на столбец внешнего запроса, поэтому его результат зависит от текущей строки и вычисляется заново для каждой строки. Концептуально это цикл: взять строку, подставить её значения в подзапрос, получить ответ, перейти к следующей.

## Сравнение со средним по группе

Задача: найти сотрудников, чья зарплата выше средней по их собственному отделу. Общая средняя здесь не годится, для каждого сотрудника нужна своя.

```sql run=company
SELECT e.full_name, e.department_id, e.salary
FROM employees e
WHERE e.salary > (
  SELECT AVG(x.salary)
  FROM employees x
  WHERE x.department_id = e.department_id
)
ORDER BY e.id;
```

Одна и та же таблица `employees` участвует дважды, под разными псевдонимами: `e` во внешнем запросе и `x` во внутреннем. Условие `x.department_id = e.department_id` связывает их: подзапрос считает среднее только по тем, кто работает в отделе текущей строки `e`.

Сотрудника без отдела в результате нет. Для него условие `x.department_id = NULL` не выполняется ни на одной строке, подзапрос возвращает NULL, и сравнение с ним неизвестно.

## Подзапрос в списке SELECT

Коррелированный подзапрос часто стоит в списке столбцов и считает что-то для каждой строки. Посчитаем число сотрудников в каждом отделе:

```sql run=company
SELECT
  d.name,
  (SELECT COUNT(*) FROM employees e WHERE e.department_id = d.id) AS staff_count
FROM departments d
ORDER BY d.id;
```

У отдела «Аналитика» значение 0, хотя сотрудников для него нет: COUNT по пустому набору возвращает нуль, а не NULL. Пока соединения не пройдены, это самый простой способ вывести данные из двух таблиц рядом.

Другие агрегаты ведут себя иначе. Дата последнего заказа каждого покупателя:

```sql run=shop
SELECT
  c.full_name,
  (SELECT MAX(o.ordered_at) FROM orders o WHERE o.customer_id = c.id) AS last_order_at
FROM customers c
ORDER BY c.id;
```

У Полины Гусевой заказов нет, и MAX даёт NULL. Так что результат различает покупателей без заказов и с заказами, и для каждого есть строка.

## Лучшая строка в группе

Одна из самых частых задач - найти в каждой группе строку с крайним значением. Самый дешёвый товар каждой категории:

```sql run=shop
SELECT p.title, p.category_id, p.price
FROM products p
WHERE p.price = (
  SELECT MIN(x.price)
  FROM products x
  WHERE x.category_id = p.category_id
)
ORDER BY p.id;
```

Для каждого товара подзапрос находит минимальную цену в его категории, и товар остаётся, если его цена с ней совпадает. Товары без категории не вошли по той же причине, что и сотрудники без отдела выше.

Равенство с минимумом сохраняет ничьи: если два товара одной категории стоят одинаково и дешевле остальных, оба попадут в результат. Проверим на данных с повторами:

```sql run=empty
WITH scores(student, subject, points) AS (
  VALUES
    ('Аня', 'математика', 90), ('Боря', 'математика', 85), ('Вика', 'математика', 90),
    ('Гоша', 'физика', 70), ('Даня', 'физика', 88)
)
SELECT s.subject, s.student, s.points
FROM scores s
WHERE s.points = (SELECT MAX(x.points) FROM scores x WHERE x.subject = s.subject)
ORDER BY s.subject, s.student;
```

У математики два лидера, у физики один.

## Ровно одна строка в группе: DISTINCT ON

Иногда нужна ровно одна строка на группу, даже при ничьей. Для этого в PostgreSQL есть DISTINCT ON. Выражение в скобках задаёт группы, а ORDER BY определяет, какая строка в группе идёт первой и остаётся:

```sql run=empty
WITH scores(id, student, subject, points) AS (
  VALUES
    (1, 'Аня', 'математика', 90), (2, 'Боря', 'математика', 85), (3, 'Вика', 'математика', 90),
    (4, 'Гоша', 'физика', 70), (5, 'Даня', 'физика', 88)
)
SELECT DISTINCT ON (subject) subject, student, points
FROM scores
ORDER BY subject, points DESC, id;
```

Сначала строки сортируются по предмету, затем по баллу от большего к меньшему, затем по `id`. Для каждого предмета остаётся первая строка. Поскольку Аня и Вика набрали по 90, победил тот, у кого меньше `id`. Последний ключ сортировки разрешает ничью предсказуемо; без него победитель выбирался бы случайно.

Выражения после ORDER BY должны начинаться с тех же, что в скобках DISTINCT ON, иначе PostgreSQL выдаст ошибку. DISTINCT ON - особенность PostgreSQL, в MySQL такой записи нет. Там для той же цели используют коррелированный подзапрос или оконную функцию ROW_NUMBER, которую вы встретите позже.

Выбирайте между двумя способами по смыслу. Коррелированный подзапрос с равенством возвращает всех лидеров. DISTINCT ON возвращает ровно одного.

## NOT EXISTS как поиск строки без более лучшей

Лучшую строку можно искать и иначе: оставить ту, для которой не нашлось строки лучше. Последняя по году книга каждого автора:

```sql run=library
SELECT b.title, b.author_id, b.published_year
FROM books b
WHERE NOT EXISTS (
  SELECT 1 FROM books n
  WHERE n.author_id = b.author_id AND n.published_year > b.published_year
)
ORDER BY b.id;
```

Книга остаётся в результате, если у того же автора нет более новой. В списке есть и «Слово о полку Игореве» без автора: условие `n.author_id = b.author_id` для неё не выполняется ни на одной строке, поэтому «более новой» не нашлось. Если такие книги не нужны, добавьте в запрос условие `b.author_id IS NOT NULL`.

## Цена коррелированного подзапроса

Раз подзапрос вычисляется заново для каждой строки, на больших таблицах он может быть медленным. PostgreSQL часто сам превращает такие запросы в более эффективные, особенно EXISTS, но для подзапросов с агрегатом на больших таблицах это не гарантируется. Если запрос работает медленно, проверьте, есть ли индекс по столбцу связи, и посмотрите план через EXPLAIN. Как это делать, объясняют в разделе о планах запросов.

## В MySQL

Коррелированные подзапросы в MySQL работают так же. DISTINCT ON отсутствует, а LIMIT внутри подзапроса с IN или ANY в MySQL не поддерживается. Обе трудности обходятся оконными функциями.
