Данные в реляционной базе разложены по нескольким таблицам, и это сделано намеренно. Название отдела хранится один раз в таблице `departments`, а у каждого сотрудника записан только номер отдела. Если отдел переименуют, правка делается в одной строке, а не в сотне. Чтобы увидеть имя сотрудника рядом с названием его отдела, строки двух таблиц нужно соединить. Для этого в SQL есть JOIN.

## Ключи и связи

Первичный ключ однозначно определяет строку таблицы. В `departments` это столбец `id`: двух отделов с одним номером быть не может. Внешний ключ - столбец, который ссылается на первичный ключ другой таблицы. В `employees` это `department_id`: в нём лежит номер строки из `departments`. База не позволит записать номер несуществующего отдела.

Связь «один ко многим» самая частая: в одном отделе много сотрудников, но у сотрудника один отдел. Внешний ключ при этом всегда стоит на стороне «многих». Так же связаны покупатель и его заказы, автор и его книги, категория и товары.

Связь «многие ко многим» одним внешним ключом не выражается. В заказе много товаров, а товар входит во многие заказы. Для такого случая заводят промежуточную таблицу, в магазине это `order_items`. В каждой её строке два внешних ключа, `order_id` и `product_id`, плюс данные самой связи: количество и цена продажи. Многие-ко-многим на деле превращается в две связи «один ко многим».

## Простейший JOIN

Соединим сотрудников с отделами:

```sql run=company
SELECT employees.full_name, departments.name
FROM employees
JOIN departments ON departments.id = employees.department_id
ORDER BY employees.id;
```

После JOIN указана вторая таблица, а после ON - условие, по которому строки считаются парой. Здесь пара - сотрудник и отдел с номером из его `department_id`. База перебирает строки и для каждой подходящей пары выдаёт одну строку результата со столбцами обеих таблиц.

Слово JOIN без уточнений означает INNER JOIN, внутреннее соединение: в результат попадают только строки, нашедшие пару. В таблице двенадцать сотрудников, а в результате одиннадцать. Стажёр Виктор Зайцев не указан ни в каком отделе, его `department_id` пуст. NULL не равен ничему, даже другому NULL, поэтому условие ON для него никогда не выполняется, и строка пропадает. Отдел «Аналитика» исчез по той же причине: ни один сотрудник на него не ссылается. Как сохранить такие строки, расскажет урок про LEFT и RIGHT JOIN.

## Псевдонимы таблиц

Длинные имена таблиц утомительно повторять, поэтому таблицам дают короткие псевдонимы, как столбцам:

```sql run=company
SELECT e.full_name, d.name AS department, d.city
FROM employees e
JOIN departments d ON d.id = e.department_id
ORDER BY e.id
LIMIT 4;
```

Псевдоним пишется сразу после имени таблицы, слово AS можно добавить, но обычно его опускают. После этого исходное имя в запросе уже не работает: `employees.full_name` вызовет ошибку, остаётся только `e.full_name`. Принято брать первую букву или короткое сокращение вроде `o` для `orders` и `oi` для `order_items`.

## Когда префикс обязателен

Если столбец с таким именем есть в обеих таблицах, без префикса PostgreSQL не поймёт, какой из них имеется в виду:

```sql run=shop error
SELECT id, title FROM products JOIN categories ON categories.id = products.category_id;
```

Ошибка говорит, что ссылка неоднозначна. Лечится префиксом: `p.id`, `c.title`. Общее правило такое: в запросе с соединением уточняйте префиксом каждый столбец, даже уникальный. Запрос читается проще, а появившийся позже одноимённый столбец не сломает его.

Раз у столбцов `p.title` и `c.title` одно и то же имя `title`, в результате получится два столбца с одинаковым заголовком. Такой результат неудобно читать и опасно отдавать программе, поэтому задайте им разные псевдонимы:

```sql run=shop
SELECT p.title AS product, c.title AS category, p.price
FROM products p
JOIN categories c ON c.id = p.category_id
ORDER BY p.id
LIMIT 5;
```

## Соединение через промежуточную таблицу

Чтобы увидеть, что лежит в заказах, соединяют `order_items` с товарами:

```sql run=shop
SELECT oi.order_id, p.title AS product, oi.quantity, oi.price
FROM order_items oi
JOIN products p ON p.id = oi.product_id
WHERE oi.order_id IN (1, 2)
ORDER BY oi.order_id, p.id;
```

Отдельно о цене. У `order_items` есть своя `price` - цена, по которой товар продан в тот момент. У `products` тоже есть `price`, это цена в каталоге сейчас. Они могут расходиться, и для суммы заказа нужна первая. Поэтому префикс здесь не формальность, а выбор нужных данных.

## Сколько строк получится

Результат внутреннего соединения по внешнему ключу обычно содержит столько строк, сколько их в таблице на стороне «многих», за вычетом строк без пары. Каждая строка `orders` находит ровно одного покупателя, и заказов в результате столько же, сколько в таблице:

```sql run=shop
SELECT COUNT(*) AS orders_total FROM orders;
```

```sql run=shop
SELECT COUNT(*) AS joined_total
FROM orders o
JOIN customers c ON c.id = o.customer_id;
```

Если же соединять в обратную сторону, от покупателя к заказам, строк на покупателя будет столько, сколько у него заказов. У Андрея Кравцова три заказа, поэтому он встретится в результате три раза. Это не ошибка, а смысл соединения: к каждой строке приклеиваются все подходящие. Об этом нужно помнить, когда дальше мы начнём считать суммы.

## Запись через запятую

В старых запросах можно встретить соединение, где таблицы перечислены через запятую, а условие стоит в WHERE:

```sql
SELECT e.full_name, d.name
FROM employees e, departments d
WHERE d.id = e.department_id;
```

Он работает и даёт тот же результат, но так писать не стоит. Если забыть условие в WHERE, получится декартово произведение, все сочетания строк, и запрос будет выполняться очень долго и вернёт гору мусора. Явный JOIN с ON не позволит пропустить условие: синтаксис потребует его.
