Таблицы хранят факты, а факты повторяются: в компании несколько менеджеров по продажам, в магазине несколько заказов от одного покупателя. Когда нужен не список строк, а перечень различных значений, после SELECT пишут слово DISTINCT. Оно оставляет в результате только по одной строке из каждой группы одинаковых.

Без DISTINCT запрос вернёт город для каждого отдела, в том числе повторяющиеся:

```sql run=company
SELECT city FROM departments;
```

С DISTINCT повторы исчезают:

```sql run=company
SELECT DISTINCT city FROM departments;
```

Москва была в двух строках, а осталась в одной. Порядок строк при этом не гарантирован, как и в любом запросе без ORDER BY. Пустое значение тоже попало в результат: это отдел без города. Для DISTINCT все NULL считаются одинаковыми и сворачиваются в одну строку, хотя в сравнениях через `=` два NULL друг другу не равны. Эту особенность мы разберём в разделе об условиях.

## DISTINCT относится ко всей строке

DISTINCT не выбирает столбец, к которому он стоит ближе. Он сравнивает строки результата целиком. Если в списке два столбца, одинаковой считается пара значений:

```sql run=company
SELECT DISTINCT department_id, position
FROM employees
ORDER BY department_id, position;
```

В таблице двенадцать сотрудников, а в результате десять строк. В отделе 3 двое менеджеров по продажам, и пара «3 и Менеджер по продажам» встречается дважды, поэтому остаётся одна. То же с двумя специалистами поддержки в отделе 4. Все остальные пары различаются и остаются как есть. Сортировка ORDER BY здесь нужна только для читаемости, её разбирает следующий урок.

Частая ошибка - написать `SELECT DISTINCT a, DISTINCT b`. Это синтаксическая ошибка: DISTINCT пишется один раз сразу после SELECT и действует на весь список. Другая ошибка - ждать, что `SELECT DISTINCT city, full_name` оставит по одному человеку на город. Имена разные, поэтому пары всегда разные, и ничего не склеится.

## DISTINCT и сортировка

Сначала убираются повторы, потом результат сортируется:

```sql run=library
SELECT DISTINCT genre FROM books ORDER BY genre;
```

В запросе с DISTINCT в ORDER BY можно указывать только то, что есть в списке SELECT. Причина проста: после склейки строк непонятно, какое из исходных значений использовать для сортировки.

```sql run=library error
SELECT DISTINCT genre FROM books ORDER BY pages;
```

## Количество различных значений

Сколько жанров в библиотеке? Это можно узнать, посчитав уникальные значения функцией COUNT:

```sql run=library
SELECT COUNT(DISTINCT genre) AS genres FROM books;
```

Агрегатные функции мы разберём в отдельном разделе, пока достаточно знать, что DISTINCT работает и внутри COUNT. Если у строки значение NULL, COUNT(DISTINCT ...) её не считает.

## DISTINCT ON в PostgreSQL

У PostgreSQL есть расширение, которого нет в стандарте и в MySQL: DISTINCT ON. Оно оставляет по одной строке на каждое значение указанных в скобках выражений, а какая именно строка останется, определяет ORDER BY.

```sql run=company
SELECT DISTINCT ON (department_id) department_id, full_name, salary
FROM employees
ORDER BY department_id, salary DESC, id;
```

Для каждого отдела остался сотрудник с наибольшей зарплатой: внутри отдела сортировка идёт по убыванию зарплаты, и из группы берётся первая строка. Сотрудники без отдела образуют свою группу с NULL.

Правило одно: ORDER BY должен начинаться с тех же выражений, что стоят в DISTINCT ON. Иначе PostgreSQL вернёт ошибку. Последним ключом сортировки ставят `id`, чтобы при равных зарплатах выбор был предсказуемым.

```sql run=company error
SELECT DISTINCT ON (department_id) department_id, full_name
FROM employees
ORDER BY salary DESC;
```

DISTINCT ON удобен для задач вида «последняя запись по каждому пользователю» или «лучший сотрудник каждого отдела». Решения без него (через подзапросы и группировки) возможны и переносимы между базами, но заметно длиннее. Мы к ним вернёмся в разделе о подзапросах.

## Цена DISTINCT

Чтобы найти повторы, базе нужно сравнить все строки результата между собой, обычно через сортировку или хеш-таблицу. На маленьких таблицах разницы не видно, на больших это заметные затраты. Если DISTINCT добавлен только затем, чтобы спрятать неожиданные дубли, лучше выяснить, откуда они берутся. Чаще всего причина в неудачном соединении таблиц, и DISTINCT её только замаскирует.
