# Управление данными LMS

Выполни конкретное поручение пользователя и проверь сохранённый результат.
Работай из Git-репозитория `app/`, соблюдай `AGENTS.md` и `CLAUDE.md`.
Существующее разрешение на эту операцию сохраняется: не запрашивай его заново
для каждого поля или запроса.

## Выбери сценарий

Читай только нужную инструкцию и актуальные исходники соответствующих коллекций:

| Поручение | Инструкция |
|---|---|
| Курс, раздел, урок, медиа, FAQ, контакты и публикация | [Учебный контент](references/content.md) |
| Темы, координаты, связи и курсы на карте | [Роадмапы](references/roadmaps.md) |
| Условия, тесты и эталоны задач | [Тренажёр](references/trainer.md) |
| Создание пользователя, роль, профиль и пароль | [Аккаунты](references/users.md) |

## Рабочий порядок

1. Определи целевую среду и результат из поручения и текущего контекста. Если
   среда действительно неясна, уточни её до записи. Проверка самого скилла
   проводится в одноразовой локальной БД, а не на продовых данных.
2. Найди документы по стабильному `slug`, `nodeId`, `edgeId` или email.
   Листай выборки до конца (`collectAllPages` либо `hasNextPage`). Несколько
   подходящих записей требуют уточнения объекта, а не изменения первой строки.
3. Прочитай поля и хуки в `src/payload/collections/`, настройки — в
   `src/payload/globals/`. Код приоритетнее примеров из документации.
4. Сохрани только запрошенные поля через авторизованный API Payload, админку
   или Local API. Сохраняй ID и прежний slug при переименовании; массивы и
   вложенные настройки предварительно прочитай и объедини с новой частью.
   Удаление, повторное создание и смена роли не являются обычной правкой текста.
5. Прочитай результат повторно. Для публикации проверь выдачу ученику и
   соответствующую страницу; для черновика — реальную видимость по access.
   Для тренажёра проверь серверный прогон.
6. Сообщи среду, изменённые объекты, проверки и ссылку на просмотр/редактирование.
   Пароли, токены, ключи и строки подключения в отчёт, файлы и память не помещай.

## Инструменты и границы

- REST: `/api/users/login`, затем `Authorization: JWT <token>`;
  `/api/<collection>`, `/api/<collection>/<id>`;
  global — `/api/globals/site-settings`. После входа проверь `/api/users/me`
  и роль администратора. Credentials бери из разрешённого окружения и храни
  в памяти процесса, не в исходниках или CLI args. Файлы, содержащие credentials,
  разбирай внутри процесса; не выводи их целиком через cat/Read, даже если
  нужны лишь имена аккаунтов. Выводи только результат проверки без значений.
- Local API по умолчанию обходит access. Для обычного управления передавай
  пользователя администратора и `overrideAccess: false`. Для составной
  атомарной операции используй одну транзакцию с общим `req`;
  последовательность REST-запросов сама по себе не атомарна.
- Не записывай контент, пароли или прогресс прямым SQL: Payload применяет
  валидацию, хеширование, права и хуки. Не отключай хуки обычных операций;
  `skipHooks` уместен там, где предусмотрен кодом, например для тестовых фикстур.
- Запись данных через API не требует push. Изменение кода каталога или
  интерфейса требует проверок и отдельного согласованного выката;
  используй `self-review` и `deploy-check` в соответствующем случае.
- После потерянного ответа изменяющего запроса сначала перечитай документ.
  Не повторяй создание/приглашение вслепую. При отказе авторизации или доступа
  останови зависимые записи и назови ошибку, не обходи access.
- Ограничения Kubernetes и восстановления Lens из пользовательских инструкций
  остаются в силе. Для этой работы Kubernetes не требуется.

## Практическая проверка

`pnpm test:integration tests/integration/cms/contentWorkflows.test.ts`
проверяет сценарии через настоящий REST-обработчик Payload и одноразовый
PostgreSQL: курс и публикация, карта, FAQ и настройки, приглашение и пароль,
задача с серверной проверкой. Почта перехватывается, реальных писем нет.

Тесты операций не заменяют проверку поведения агента. Для неё дай отдельное
поручение на локальном тестовом сервере, например создать черновик курса,
затем переименовать его с сохранением ID и slug.
