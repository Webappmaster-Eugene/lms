Проверь собственные изменения так, как их проверял бы придирчивый ревьюер. Это §2 правил проекта из `CLAUDE.md`, вынесенная в процедуру.

## 1. Определи объём

```bash
git diff              # незастейдженное
git diff --cached     # застейдженное
```

Если diff пуст — возьми список файлов из `$ARGUMENTS`.

## 2. Пять вопросов к каждому изменённому файлу

1. **Корректность.** Делает ли код то, что задумано? Обработаны ли все ветки? Что будет на пустом списке, на первом элементе, на последнем?
2. **Типы.** Есть ли неявный `any`, `as`, non-null assertion? `null` и `undefined` различаются там, где это важно?
3. **Ошибки.** Что произойдёт при отказе БД, при пустом ответе Payload, при невалидном вводе из формы? Ошибка проглатывается молча или попадает в лог?
4. **Побочные эффекты.** Не ломает ли это соседние подсистемы? Хук `afterChange` не зациклится? Запрос не выполняется в цикле по элементам?
5. **Чистота.** Остался ли мёртвый код, отладочный вывод, лишний импорт, закомментированный блок?

## 3. Специфика этого проекта

- **Хуки Payload.** Начисление баллов, сертификаты, достижения идут через `afterChange`. Проверь: защита от повторного срабатывания есть? `context: { skipHooks: true }` проставлен там, где хук пишет в коллекцию, у которой есть свой хук?
- **Серверные и клиентские компоненты.** `'use client'` стоит там, где реально нужен стейт или эффект? Секреты и вызовы Payload не утекли в клиентский компонент?
- **Права доступа.** Новая коллекция имеет явный блок `access`? Новый API-роут проверяет `payload.auth()` до любой записи?
- **Миграции.** Изменение схемы сопровождается миграцией, и миграция совместима с уже работающим кодом (expand-contract).

## 4. Найди минимум три улучшения

Даже если код выглядит готовым. Кандидаты:

- имя переменной, которое приходится расшифровывать по контексту;
- условие, которое читается через отрицание отрицания;
- ранний выход (guard clause) вместо вложенности;
- тип, который можно сузить с `string` до литералов;
- сообщение об ошибке, по которому нельзя понять, что делать дальше;
- комментарий, объясняющий «что» вместо «почему».

## 5. Исправь найденное сразу

Не оставляй «на потом» — после правок прогони:

```bash
pnpm lint
pnpm typecheck
pnpm test
```

Изменения в логике, покрытой тестами, должны сопровождаться правкой тестов. Если поведение изменилось, а тест остался зелёным — тест проверяет не то.

## 6. Отчёт

- Что нашёл и что исправил — списком, по существу.
- Что осознанно оставил как есть и почему.
- Вердикт: **Ready to commit** или **Needs more work** с перечнем оставшегося.
