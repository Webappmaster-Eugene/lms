# MentorCareer LMS

Учебная платформа: Next.js 15 App Router + Payload CMS 3 на PostgreSQL, тренажёр
задач с исполнением пользовательского кода в песочнице, отдельный лендинг на Astro.
Код живёт во вложенном Git-репозитории `app/`; родительская папка `107.lms` —
рабочий каталог, в Git она не входит.

Отвечай по-русски. Тексты интерфейса и писем — тоже по-русски.

## 1. Где что лежит

| Что | Где |
|---|---|
| Git-репозиторий, все команды | `app/` |
| Страницы и API | `app/src/app/` — группы `(auth)`, `(frontend)`, `(payload)`, `api/` |
| Payload: коллекции, хуки, доступы, письма | `app/src/payload/` |
| Конфиг Payload и список коллекций | `app/src/payload.config.ts` |
| Миграции БД | `app/src/migrations/` + реестр `index.ts` |
| Бизнес-логика и утилиты | `app/src/lib/` |
| Серверная песочница тренажёра | `app/src/server/trainer/` |
| Каталог задач тренажёра (кодом) | `app/src/data/trainer/` |
| Компоненты | `app/src/components/` |
| Тесты | `app/tests/` — `unit/`, `components/`, `smoke/` |
| Лендинг (отдельный npm-пакет) | `app/landing/` |
| Документация | `app/docs/` |
| Инфраструктура агентов | `app/scripts/codex/`, `app/docs/CODEX.md` |

`app/scripts/build-harness.mjs` — это харнесс **тренажёра** (рантайм песочницы),
он не имеет отношения к харнессу агентов в `app/scripts/codex/`.

## 2. Команды

Пакетный менеджер — pnpm 10 (закреплён `packageManager`, обычно через corepack).
Лендинг `landing/` — отдельный пакет со своим `package-lock.json` и `npm`.

```sh
pnpm dev           # предварительно копирует Monaco и собирает харнесс тренажёра
pnpm lint
pnpm typecheck
pnpm test          # vitest: проекты unit (node) и components (jsdom)
pnpm build
pnpm smoke         # lint + typecheck + test + build именно в этом порядке
```

Порядок в `smoke` не случайный: линтер и типы отрабатывают за секунды, сборка —
за минуты. Ставить сборку первой значит долго ждать ради неиспользованного импорта.

```sh
pnpm payload migrate:create   # миграция после изменения схемы коллекции
pnpm generate:types           # src/payload-types.ts
pnpm generate:importmap
pnpm seed                     # базовый сид
pnpm seed:trainer             # каталог задач тренажёра, идемпотентно
```

`pnpm build` требует `DATABASE_URL` и `PAYLOAD_SECRET`: Payload собирает конфиг на
этапе сборки. Без них сборка не проходит — это не повод объявлять её пройденной.

Postgres локально не предполагается. `pnpm test` БД не поднимает и не требует.

## 3. Правила работы

**Push в `main` = деплой.** Прод собирается из ветки `main` репозитория
`Webappmaster-Eugene/lms` через Dokploy. До push обязательны `pnpm smoke` и
скилл `deploy-check`. Force push и `reset --hard` — только по явной необходимости
и с разрешения. Чужие незакоммиченные изменения в коммит не включать.

**Миграции применяются на старте контейнера** (`prodMigrations` в
`src/payload.config.ts`). Несовместимая миграция роняет прод, а не откладывается
до ручного запуска. Схема изменений — expand-contract: сначала добавить колонку,
следующим выкатом переключить код, третьим удалить старое. Удаление в один шаг
ломает промежуток, когда новая схема уже применена, а старые контейнеры ещё отвечают.

**Секреты только из `process.env`.** Ни в коде, ни в логах, ни в отчётах, ни в
памяти агента. `.env`, `media/`, дампы БД не коммитить.

**Изменения прода — только с подтверждением пользователя.** Перевыкат стирает
следы: сначала назови причину, потом предлагай действие.

## 4. Соглашения кода

- TypeScript strict. `any`, non-null assertion и `console.log` запрещены линтером;
  исключения перечислены в `eslint.config.mjs` и расширять их без причины не нужно.
- React 19, App Router. Серверные компоненты по умолчанию; `'use client'` — только
  там, где нужен браузер.
- Одинарные кавычки, без точек с запятой, 2 пробела — как в существующих файлах.
- Импорты через алиасы `@/…` и `@payload-config`. Алиасы продублированы в
  `vitest.config.ts` — при изменении `tsconfig.json` править оба.
- Комментарии узкие и только «почему». «Что делает» видно из кода.
- Ошибки не проглатывать молча: лог и внятное сообщение пользователю. Пустой
  `catch` — дефект, а не стиль.
- Выборки из Payload делать постранично (`src/lib/paginate.ts`), а не до
  фиксированного лимита: каталоги давно переросли первую сотню документов.
- Составные операции с побочными эффектами (начисления, сертификаты, уведомления)
  выполнять в общей транзакции — хуки уже так написаны, не расшивать.
- Сообщения коммитов: `type(scope): суть по-русски`, в настоящем времени.

## 5. Доступы и безопасность

- `src/middleware.ts` закрывает всё, кроме `PUBLIC_PATHS` (`/login`,
  `/forgot-password`, `/reset-password`, `/admin`, `/api`) и перечисленной статики.
  Слаги приходят из CMS, поэтому статика определяется поимённо, а не по расширению.
- Права коллекций — `src/payload/access/`: `isAdmin`, `isAdminOrSelf`,
  `isAuthenticated`. Новая коллекция без явного `access` открыта — это дефект.
- Владелец документа проставляется хуком `assignOwner`, а не приходит от клиента.
- CSP, `X-Frame-Options`, `Referrer-Policy` заданы в `next.config.mjs`. `connect-src
  'self'` — поэтому ассеты Monaco копируются локально, а не берутся с CDN.
- Изменения в middleware, `access/` и хуках Payload типами не проверяются: к ним
  нужен тест. Смоук-тесты `tests/smoke/accessControl`, `routeAccess`,
  `securityHeaders` существуют именно для этого.

## 6. Тренажёр

Полное описание — `app/docs/trainer.md`. Что важно помнить при изменениях:

- «Запустить» считает в браузере (iframe без `allow-same-origin`), «Отправить» —
  на сервере в V8-изоляте. Клиентский результат на сервер не отправляется:
  `POST /api/trainer/submit` пересобирает прогон из своей копии тестов. Единственный
  источник истины для прогресса — серверный прогон.
- Изолят живёт в отдельном процессе (`runner-child.mjs`) с пустым окружением:
  рядом нет ни `DATABASE_URL`, ни `PAYLOAD_SECRET`. Это граница безопасности —
  не прокидывать туда переменные ради удобства.
- Таймеры во всех песочницах виртуальные. Тесты двигают время через `__clock`.
- Каталог задач лежит кодом; `tests/unit/trainer/catalog.test.ts` проверяет, что
  эталон проходит тесты, а шаблон — нет. Сломанную задачу закоммитить не выйдет.
- `harness-source.generated.ts` генерируется `scripts/build-harness.mjs` и
  закоммичен; при расхождении падает `harnessSource.test.ts`.
- Нужен Node 22: `isolated-vm` не собирается под Node 20.

## 7. Прод

| Что | Значение |
|---|---|
| Сервер | Dokploy на `root@217.199.254.38` |
| Приложение | compose `lms-mentor-<hash>`, хеш меняется при пересоздании |
| Сервисы | `lms-mentor-app` (3000), `lms-mentor-db` (postgres:16), `lms-mentor-landing` (80) |
| Домены | `learn.mentorcareer.ru`, `promo.mentorcareer.ru` |
| Тома | `…_lms-pgdata`, `…_lms-media` |

Имена контейнеров находить динамически. На сервере живут чужие стеки — фильтровать
по `lms-mentor`. Новая переменная окружения должна попасть в три места сразу:
`.env.example`, `docker-compose.yml` и Dokploy UI; `NEXT_PUBLIC_*` — ещё и как `ARG`
в `Dockerfile`, иначе в браузере будет `undefined`.

Диагностика прода — скилл `prod-check`, процедуры в `app/docs/`:
`db-password-rotation.md`, `seed-production.md`.

## 8. Скиллы

Источник методологии — `app/.claude/skills/`:

- `self-review` — строгая проверка собственных изменений перед коммитом;
- `deploy-check` — преддеплойная проверка, вердикт READY или BLOCKED;
- `prod-check` — диагностика прода по SSH.

Codex видит те же скиллы через адаптеры в `app/.agents/skills/` — они читают
оригиналы, а не пересказывают их. После изменения скиллов, настроек Claude или
документов `expert_info/lms/` нужен `pnpm codex:sync`.

## 9. Завершение работы

После изменений — `self-review` и относящиеся к ним проверки. Не выдумывай
замечания ради фиксированного количества: исправляй подтверждённые дефекты,
остальное перечисли как наблюдения.

В итоговом ответе: что сделано, какие проверки реально выполнены и что осталось
непроверенным. Недоступный инструмент или отсутствующая переменная окружения —
это пропущенная проверка, а не пройденная; так и пиши.
